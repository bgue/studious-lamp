# AGENTS.md — tl-mcp

Read the root `AGENTS.md` first. These rules add to it.

- No business logic here. Tool and resource bodies call `tl_core` services through `ctx.factory(True)`; no SQL, no ledger access.
- `server.py` owns tool names, schemas and descriptions (the text an agent reads); `tools.py` and `resources.py` own the bodies. Every body runs inside `guarded(...)`, which checks the identifier parts, calls the authorise hook with a quoted resource name, and turns expected failures into `ToolError` or `ResourceError`.
- `lake_query` only forwards to `tl_lake.LakeQueryService`, which owns the guard, limits and audit log; never widen what it accepts here, and keep the answer cap below the service's own. `GuardError` becomes `refused: ...`, any other `LakeError` a `ToolError`.
- Record-changing tools are propose-only (`write_tools.py`): they build the command, call `proposals.submit` and return the pending proposal. Never call a record handler from a tool, never add a tool that accepts, rejects or fails a proposal, and never add a direct-write mode (the REST API refuses record-changing commands from `agent:` tokens too, B15): who may write directly is the permission model, a human gate (ADR-0005). `modes.py` refuses `write` with the human-gate message. `post_feed` is the one direct write (a post is a message); it carries the agent's actor and `source=mcp:<id>`.
- Every write tool runs inside `guarded`, takes the actor from the server (never from an argument), and tags `source` through `proposals.source_for`. A new write tool needs a hook test, a bounds test and a source test in `tests/test_mcp_write_tools.py`.
- An agent never sets a setting: `propose_setting_change` only submits a `ChangeSetting` proposal, and `get_settings` only reads. Do not add a tool that changes a setting, and do not add an `accept_risk` argument anywhere; the person who accepts supplies it.
- Bound every new string input with `Field(max_length=...)`; the query text limit is the parser's (`MAX_QUERY_LENGTH`). Free-form JSON is bounded as text with `check_json`. `test_every_string_the_tools_accept_has_a_length_limit` fails on a string without a limit.
- `mcp` is 2.x: `MCPServer` (not `FastMCP`), `mcp.Client(server)` for an in-memory client. Tests call `server.call_tool` and `server.read_resource` in process; no async plugin, use `asyncio.run`.
- The dev server (`tl_mcp/dev/`) is separate from the product server: never import it from `server.py` or register a dev tool there. Every dev tool body runs inside `tl_mcp.dev.runtime.guarded`, takes its database only from `ctx.target` (already checked by `guard.resolve_target`), starts child processes with an argument list and `ctx.child_env()` (never a shell, never the server's full environment), and returns no absolute server path.
- `query_db` is SQLite only (decision C4). Do not add a Postgres path on a function deny-list: `ts_stat` and `ts_rewrite` run SQL strings, so a split name defeats any text screen (L-P0-I8C-1). It needs a non-superuser reader role and a function allow-list first. A change to `guard.py`, `sqlguard.py` or `query.py` needs a test that names the case it must still refuse, and a fresh-context security review.
- A new dev tool: one `tool_<name>.py` with `register(server, ctx)`, listed in `dev/server.py`, bounded parameters (`test_every_string_the_dev_tools_accept_has_a_length_limit`), and tests with `DevHarness` (`tests/dev_harness.py`, fixture `dev_env`).
- Type tools (`type_tools.py`) are read-only and bodies are read only through `bodies.read_body(ctx.factory, ctx.objects, ...)`, which quarantines a damaged body; without an object store the tool says so (`NO_STORE`). Never add a tool that stores a body: agents propose, and a proposal carries no body (B11; proposable bodies are a follow-up). Tool descriptions are what an agent reads: keep implementation notes in comments.
- Identity (P1-I0): the server acts as the agent that `TL_AGENT_TOKEN` belongs to; there is no `--actor`. `tl_mcp.identity.token_authorizer` is the `authorize_hook` of the real server: it looks the token up on every call (`principal_for_bearer`) and runs the role `Authorizer`, which allows an agent only `mcp.*`. Never cache the principal, never read the token from argv, and never put it in a message, log line or error (`test_mcp_identity.py` checks the texts). `build_server` keeps its `actor` and `authorize_hook` parameters for tests and in-process use; the entry point is the only caller that passes a token hook.
- The agent's allowance is an explicit list (`tl_mcp.identity.MCP_ACTIONS` on top of the API's `AGENT_ACTIONS`), not a prefix: a new tool or resource is closed to agents until its action is added there. `test_every_registered_tool_and_resource_is_decided_and_nothing_stale_is_listed` registers the real server and fails on a missing or stale entry.
- `--db` and `TL_DB` are a `DbTarget` (SQLite path or `postgresql://` URL); the server runs on `tl_adapters.backend.open_backend`. A caller that starts this server (the simulator) passes the target and the token in the child's environment, never a URL on the command line. `query_db` and the other dev tools stay SQLite only (decision C4).
- Thread tools (`thread_tools.py`): `post_thread_message` is direct and labelled with the agent; `propose_dispatch` plans as the agent with nothing run and files a proposal; the tools take no `source`, `correlation_id`, `holds` or roles. A new thread tool joins `tests/test_mcp_thread_walk.py`.
