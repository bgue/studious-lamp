# AGENTS.md — tl-sim

Read the root `AGENTS.md` first. These rules add to it.

- The simulator acts only through the suite's public interfaces (brief 29.1): `tl_api.client.ApiClient` for reads and writes, the MCP server for proposals. Never import a ledger, unit of work, projection, adapter, `sqlalchemy` or a `handle_*` function; `tests/test_contract_and_boundary.py` reads the imports and fails. Command models, error classes and `tl_api.tokens` (dev identity, ADR-0005) are allowed.
- `types.py` is the frozen actor interface of `docs/tickets/P0-I6/FANOUT.md`, kept verbatim (a test compares them). Change it only by orchestrator decision.
- Determinism is the product. No wall clock, no global `random`, no `uuid`, no set or dict-order decisions in an actor or in the orchestrator. Randomness comes from `SimContext.rng`, which is `rng.actor_rng(seed, actor, day)`. An actor draws in the order its docstring lists; the actor tests pin the first draws. Simulator v0 makes no LLM calls (FANOUT D6).
- An actor writes only through its `Recorder` (`actors/base.py`), which makes the call and appends the matching `GroundTruth` line in one step. Ground truth never holds a server-made id (ULID): records are named by key, links by `from relation to`, posts by actor and time.
- Identities (WS-B B15): the API refuses record-changing commands from `agent:*` tokens, so the role actors are `user:sim-<role>` (they stand in for people) and the only agent is `agent:sim-assistant`, which proposes over MCP. Never give an actor an `agent:` identity to make it write.
- Keys are assigned by the client (`client.Keys`): a simulation scope `project:sim-<run>` has a dash that the numbering pattern's `{project}` refuses, so the suite cannot number records there.
- The agent proposes and a person decides: `Recorder.propose` (MCP, a refusal such as a duplicate link is `None` and leaves no ground truth) and `Recorder.decide` (the approver, through `ProposalDesk`). Never let the assistant write a record: the API refuses it (`agent_must_propose`) and `sim_assert` checks the actor of every event.
- Simulated time is the `X-TL-Effective-At` header on command requests, honoured by the API only for `project:sim-*` scopes (FANOUT D5). Events written over MCP are stamped with real time (the MCP server does not read the header).
- The MCP server is a remote door and is narrower than the CLI: `sim_create` takes a bundled scenario name only (`load_bundled_scenario`, real path inside `seed_dir()/scenarios`), errors shown to it are `ScenarioError.public` (no path, file content or parser text), every tool calls the authorise hook first (`sim.<tool>`), and injection arguments are capped in `InjectSpec` (count at most 20, strings 2000 characters, 16 keys, scalars) with at most 100 queued per run. Never route a filesystem path to it.
- Nothing passes by doing nothing: `Recorder.propose` raises every MCP refusal except a duplicate link; `sim_assert` reports `actor_silent` for an enabled assistant (guaranteed at least one proposal a day) or approver that left no ground truth, `agent_wrote` for an agent event other than a proposal, post or its link suggestion, and `rejected_link_made`. `Simulation.create` asks the connector to `check` the scenario first (the agent needs a ledger file) so a bad setup fails before anything is written. MCP calls time out after 30 s (`McpUnavailableError`, a `RunError` with the server's own stderr).
- A server the simulator starts (`dev/seed/seed.sh`, the demo) runs under `setsid` and is stopped by killing its process group, because `$!` of a backgrounded function is the wrapper, not the server.
- A run is a directory (`run.json` mode 0600 with the dev tokens, `ground_truth.ndjson`). A step that dies leaves `in_progress` set and the run refuses to continue; create a new run.
- `testing.FakeWorld` mirrors the real suite where actors depend on it (the sample `core.review` workflow, its guard, and the errors it raises). Change it only together with the end-to-end test that shows the real suite behaves that way.
- Tests: `tests/test_end_to_end.py` and `tests/test_http_client.py` run the real API app in process; everything else runs on `FakeWorld`. No network, no sleeping.
- The assistant's MCP server needs a real agent token (P1-I0, ADR-0009): `stdio_caller(db, token)` puts it in the child's `TL_AGENT_TOKEN`, never on its command line, and `HttpConnector.check` refuses an assistant without one. The simulator cannot make accounts (it never touches the ledger): under `tl`, `tl_cli.sim_agent` makes the agent `sim-assistant` and a 2-day token on the dev ledger (dev, demo and test environments only) and `tl_sim.cli.AGENT_TOKEN_SOURCE` carries it in; standalone, `TL_SIM_AGENT_TOKEN` must name a token an admin issued. The role actors keep dev tokens (`user:sim-*`, honoured only where `TL_ENV` is dev, test or ci). The agent's tokens rotate: a run revokes the expired ones and then the oldest while 10 or more remain (`tl_cli.sim_agent.KEEP`), so up to ten `tl sim` processes at once keep working and the 20-token allowance never fills; `issue_token` itself refuses outside a dev, demo or test environment, and a person account named `sim-assistant` is a clear error.
- The ledger of a run (`SimEnv.db_path`, `connector.db_path`) is a `LedgerTarget` (`tl_sim/target.py`: a `Path`, or a Postgres URL as text), carried and never opened: the simulator imports nothing from `tl_adapters` (brief 29.1, `test_contract_and_boundary.py`). Start the MCP child with `stdio_caller(db, token)`: `TL_DB` and `TL_AGENT_TOKEN` go in its environment, never on its command line. The child validates the target; only a ledger file is checked for existence here.
