`specs/phase2-wave-plan.md` from wave 2 on, and the "every new log ships its web page in the same increment" rule
(decision 3 of that plan) for waves 3 and 4. Side quests are not done now: they go to `DEFERRED.md`.

## Ground rules
- Delegate to the cheapest tier that can do the work: Haiku tickets first, Sonnet builder pieces only for core work.
- Keep the 10% slice rules (stop new work at baseline + 9 points, stop running work at baseline + 10).
- Testing: each ticket's own gate, plus one full per-folder run at each wave close (the four-part gate does not fit 16 GB).
- No extra security reviews, frequent full runs, refactors or nice-to-haves unless they block the work in hand.
- Push as work lands; main equals the trunk after each wave close.

## Punch list brought forward: cost
Phase 3 I1/I2 plan M5 (Issue engine, inspections, deficiencies, calibration). A punch list alone needs a record type,
its workflow, a log screen, CLI verbs, agent read tools and the generator section, about 3–4 weekly points. It lands
right after wave 3, before wave 4. Risk: when Phase 3 builds the full Issue engine, the punch item becomes one of its
types; the schema is written for that (a `quality.` record with the Issue engine's state names), so the rework should
stay under one point. Inspections and deficiencies stay in Phase 3; the generator's quality section fills punch items
first and switches inspections and deficiencies on when those types exist.
