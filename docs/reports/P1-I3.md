## Outcome
Objective met: yes. A person (or an agent, by proposal) can turn a source file into validated, published records without leaving the ledger.

- A file attached to a document revision is read by an extractor plugin (`tabular`, `pdf`, `ocr`, from `tl-extract`) in a child process under a resource envelope, and the result is stored as a derived document: rows and a report are files, the record, its passes and its jobs are events (ADR-0014).
- The rows are validated against a registered JSON Schema (`DocumentSchema`, company or project scope, semver), also in the envelope. The report names row and field.
- A derived document is compared with the pass before it, or with the previous revision's data (by key column).
- Publishing is create-only and correlated: tags (admin) or documents (document controller) are created through the module's own commands with provenance (`src.doc.<number>@<revision>`) and a `derived_from` link, and one `Published` event records the ids it made. Compensation (admin) reverses those recorded ids, all or nothing; the ledger only grows.
- Agents propose only (`start_extraction`, `propose_import`); accepting a proposal needs the access of the command it carries; `validate_against_schema` reads the stored report.
- Entry points: CLI `tl derive` (schema, open, content, start, worker, ls, jobs, cancel, show, report, rows, diff, check, validate, publish, compensate), API (reads and routes, `ApiClient`), MCP (five tools), TUI (F11 derived documents, job monitor, publish preview and undo).

Demo path verified: `just demo P1-I3` passes its eight clauses on SQLite and on Postgres, with the real `pdf` and `tabular` extractors (the fake extractors are used only by the unit tests). Verified on a fresh clone: not repeated; the demo and the gates ran on the final tree of the `p1/i3a` worktree.

| Finding | Fix (commit) |

| HIGH 2 `tl derive --actor` was unchecked | The option is hooked and checked, a walk-the-tree test, the stubs of T14c and T14d carried their gates as final code (a4182db) |
| MEDIUM 3 unpickling | The child answers a tag, a length and JSON; nothing is unpickled (a75b464) |

| MEDIUM 5 unbounded parts of a result | Names, notes, problems, metadata, sheet names and profiles are bounded in the parent (a75b464) |
| MEDIUM 6 the child inherited the environment | Scrubbed environment, a limit that cannot be set fails closed, written down as "not a sandbox" (a75b464, ADR-0014) |
| LOW 7 to 10 | Bounded parse cache; a queue row without a record is failed in a savepoint; `derived_from` reserved and the trust in provenance written down; Void is a controller's act; `ExtractorLoadError` is a fixed 503 (8656dc9) |

## Showcase
The demo state for these is the ledger the script builds: `just demo P1-I3` (it removes its ledger afterwards); to look at it by hand run clauses 1 to 5 of `dev/demos/P1-I3.sh` against a dev ledger (`tl init --dev`, `tl login demo`), with `TL_OBJECT_ROOT` set. The samples are in `schema/fixtures/document-schemas/`.

1. **A spreadsheet that tells the author which cell is wrong.**
   - Where: `uv run tl derive schema register instrument-index.yaml --company`, then `tl derive open ISD-001 A --schema instrument-index --project P123`, `tl derive content ISD-001@A/instrument-index schema/fixtures/document-schemas/instrument-index@1.0.0.invalid.csv --project P123`, `tl derive start ...`, `tl derive worker --once`, `tl derive report ISD-001@A/instrument-index --project P123`. In the TUI: `F11`, highlight the document, `d` toggles report and diff.
   - Standard activity: loading an instrument index from a spreadsheet and checking that every row is complete and in the allowed lists.
   - Novel approach: the check is a JSON Schema the company registers once and versions, applied to the stored rows in a resource-limited child process, so a bad pattern or a hostile file ends as a fixed, named failure and the worker goes on to the next job.
   - Unique value: the person sees "row 6, column `fail_action`: `OPEN` is not one of FC, FO, FL" before anything is created, and the same report is what the API, the TUI and an agent read.
2. **Reading a corrected file again and seeing exactly what changed.**
   - Where: attach `instrument-index@1.0.0.sample.csv` with `tl derive content`, start and run the worker, then `tl derive diff ISD-001@A/instrument-index --project P123 --rev 3`; TUI `F11`, `d`.
   - Standard activity: comparing this version of a register with the last one.
   - Novel approach: every read is a numbered pass kept with its rows, and the diff is by key column (added, removed, changed cells with old and new), not by line.
   - Unique value: a reviewer approves "one cell changed in row 6" instead of rereading 40 rows.
3. **Publishing 40 tags that remember where they came from, and taking them back.**
   - Where: `tl derive publish ISD-001@A/instrument-index --project P123` (the preview: `create 40`, dry run), as an admin `tl derive publish ... --apply`, then `tl derive compensate ... --reason "..."` and `--apply`. TUI: `F11`, highlight, `p` (preview and approve), `u` (undo).
   - Standard activity: loading the tags of a drawing into the tag register.
   - Novel approach: one correlated import through the module's own commands; each tag carries `provenance` (`src.doc.ISD-001@A`) and a `derived_from` link to the derived document; compensation reverses the ids the publication recorded, all or nothing, and the history stays.
   - Unique value: "where did this tag come from, and can we undo that import" has an answer that does not depend on anyone's memory; a user cannot publish, a document controller publishes documents, an admin publishes tags.
4. **An agent that can only ask.**
   - Where: an MCP client calls `propose_import` (the demo's `p1_i3_demo.py propose`); `tl proposal ls --project P123` shows it pending with the number of rows; a user's `tl proposal accept` is refused (needs the admin role); the admin's succeeds and the 10 tags exist.
   - Standard activity: an assistant preparing an import for a person to approve.
   - Novel approach: the agent has no way to write; its proposal is checked by a dry run, and accepting it needs the access of the command it carries, so an agent cannot widen what a person may do.
   - Unique value: the time saved is the agent's, the decision stays a person's, and the record shows who proposed and who accepted.
