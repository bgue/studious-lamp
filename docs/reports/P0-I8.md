## Deviations from plan
- The deviations of workstreams A to D are in their reports; the ones a reader of the phase must know are collected in `docs/reports/PHASE-0.md` §4: `F9` for about:config, `query_db` SQLite only, the stricter dev guard, the extension-type refusals (directory-backed storage, `incoming/`), the performance misses D1 to D6, the feed projector change D-S65 and the amendment of build spec 03 §9 for the extra indexes.
- Workstream E dispatched no tickets (see `docs/tickets/P0-I8/README-E.md`): the candidate failed the checklist, and a smaller number of agents was safer after three usage-limit cutoffs.
- The exit demo runs the TUI headless (Textual Pilot) against a real server; it does not drive a real terminal. Its webhook receiver is a stdlib server on loopback that checks the Standard Webhooks recipe itself, standing in for an external system as D14 allows. MCP legs are propose-then-accept, because MCP writes are propose-only (B15, ADR-0005).
- Because the demo's simulated scope (`project:sim-exit`) cannot be auto-numbered (L-P0-I6C-1), the demo supplies record keys.

## Escalations and decisions
- No escalation was needed in workstream E. Nothing blocked on a human gate; none was crossed.
- Decisions made by the supervisor: the demo's independent receiver instead of the library's `DevReceiver`; the Postgres restore leg uses a dedicated scratch database (`tl_demo_<pid>_<n>`), never `tl_test` or `tl_test_bench_*`, dropped in a `finally`; a SKIP, not a PASS, when Postgres is unreachable.
- Findings from the audit that change the plan: upgrade tooling and "comments" were in §16 but in no increment ticket (L-P0-I8E-3); the CI workflow has never run.
