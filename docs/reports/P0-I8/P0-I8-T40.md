## Deviations
Two tests and one schema behaviour differ from the ticket's test list; see the first two items.

1. The marker `"slow"` and the 21-path call are rejected by the tool schema, not by the guard. The ticket's *Tests to add* expects both to raise a `ToolError` matching `refused` and to write a `refused` audit line. The ticket's Step 1 types `marker` as `Literal["parity", "requires_postgres"] | None` and `paths` with `max_length=20`, so the SDK's pydantic validation rejects them before the body runs. The tests assert that a `ToolError` is raised, and for `marker="slow"` that no audit line is written. I kept Step 1 as written. See Open questions.
2. The `refused` assertions for the other refusal cases hold as specified: a path outside the allow-list (`../etc`, `/etc/passwd`, `--co`), a keyword with shell characters, and no filter at all.
3. Smaller choices within the spec:
   - `Popen` also gets `encoding="utf-8", errors="replace"` next to `text=True`, so non-UTF-8 pytest output cannot raise during `communicate`.
   - A report file is written on timeout too, with `exit code: -1`.
   - Refusal happens when no path, marker or keyword is given, even if `adapters` is given (Step 2 read literally).
   - The `paths` default is `Field(default_factory=list)` with `# noqa: B008`, because `[]` triggers B006 and the repo has no list-parameter precedent.
   - Report pruning orders files by name (the timestamp prefix), not by mtime.
   - The timeout test's "no child left" check reads `/proc` (Linux only); on other platforms it is vacuous.

## Learnings (proposed)
- Literal and `max_length` violations on a tool's arguments are rejected by the SDK before the tool body. No `guarded` audit line is written, and the message is pydantic's "validation error", not `refused:`. A test that needs an audit line has to use a value that passes the schema.
- The existing dev-server tests write `dev/data/dev-mcp.log.jsonl` into the real repository's `dev/data/` (git-ignored, from `dev/main.py`). My tests do not write there.
- The ticket's *Context* list does not include `errors.py`. Its `DevGuardError` and `DevToolFailure` are imported by `guard.py` and `runtime.py`, so importing them by name worked without reading the file.
