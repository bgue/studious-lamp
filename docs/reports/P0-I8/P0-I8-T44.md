## Learnings (proposed)
- `tl_core.webhooks.transport.ResolvedTarget.scheme` is `Literal["http", "https"]`, but `tl_mcp.dev.guard.LoopbackUrl.scheme` is plain `str`. The ticket's step 3 (`ResolvedTarget(scheme=target.scheme, ...)`) fails pyright. Fix used here: a local `Literal` annotation with `"https" if target.scheme == "https" else "http"`. A future ticket could type `LoopbackUrl.scheme` as the same Literal instead.
- `guarded` maps `DevGuardError` (a `ValueError` subclass) before `ValueError`, so a guard message gets a `refused: ` prefix. A `ValueError` raised from a tool body (unknown event type, malformed secret) gets `ValueError: ...` and is not a refusal.
- `check_loopback_url` returns the bracketless IPv6 address (`::1`), so the ticket's `target` format `"<ip>:<port>"` is ambiguous for IPv6. I followed the ticket as written.

## Open questions / Blocked
none blocking. Questions for the supervisor:
1. **Credentials in the audit file.** `guarded` writes the `url` argument verbatim to the audit file, as the ticket specifies. A URL carrying userinfo (for example `http://user:pw@127.0.0.1/`, which is refused) therefore puts `user:pw` into `audit.jsonl`. The ticket says never to put the *secret* in the audit, but does not say whether a URL password counts. I did not redact it, because the ticket names the audit detail exactly. Please decide whether the audit should drop or mask userinfo (that would change the `refused` test expectation to match the masked URL).
2. **IPv6 target text.** `target` is `"<ip>:<port>"` per the ticket, so `::1` gives `::1:<port>`. Should it be bracketed as `[::1]:<port>`?
