## Learnings (proposed)
- `object_secret()` (tl_adapters/objectstore) uses TL_OBJECT_SECRET whenever it is set, whatever TL_ENV is; so `TL_ENV=demo` can use the object store. The "only dev can" fallback in the ticket does not apply.
- The overlay `dev/data/demo-project-schema` is made of symlinks into the fixtures; a copy needs `cp -RL` or the bundle carries dangling links.
- `just demo-project` passes `--objects` and `--sections` through to the generator unchanged.

## Open questions / Blocked
1. **Documents bytes are not in the bundle (decision needed).** The documents section uploads files through `FileService` (`dev/seed/demo_project/world.py` `upload` → `complete_upload`), so the object store under `ledger/files` holds the document blobs. The ticket fixes the listing to three items, so `ledger/files` is left out. The starter's document records will point at missing bytes. Options: add `ledger/files` to the archive (changes the listing contract and the test), or accept it and say so in START.txt. I did not change the listing. Not checked in a running client.
2. The try-it `TL_OBJECT_SECRET` value is written in START.txt by design. I read "no other secret" as: the demo password and the documented try-it value are the only secret-like strings. Please confirm.
3. `just release-starter` does not run `dev/release/build.sh`, and build.sh empties `dist/release-<version>/`. Run build first, then the starter; the starter's SHA256SUMS line is kept only if build runs first.
4. `tl serve` and `tl-tui --remote` were not started (interactive and long-running); START.txt's commands are from the ticket and the code's flags, not from a run.
5. macOS: bsdtar has no `--sort=name`; the script warns on stderr and the archive is not byte-identical there. The header comment says so.
