## Deviations
- `300-T-101` is written with `RecordTag` (admin), not `CreateTag`. Mnemonic `T` is not in `standards.yaml` and the sequence has three digits, so the pattern check refuses it; it is kept as a recorded violation (`number_status = violation`), the same route the generator already uses for legacy numbers.
- The anchor P&IDs are registered with `revision_scheme="alpha"`. The project's P&IDs get numeric codes (`0`, `1`), but the ticket asks for revisions A and B.
- `P200-200-PID-4701` is made `restricted` after its revision is issued, not at registration. A restricted record is hidden from the writer's default viewer, so the workflow step of `RegisterDocument` fails with "no record".
- `P200-200-PID-4701` has `page_count = 3` on its rendition, but `make_pdf` produces one page. The "3 sheets" is recorded as the sheet count, and the PDF text says "Sheets 3".
- `ANCHOR_TAGS` and `ANCHOR_DOCUMENTS` are tuples. `200-V-1027` collided with a generated tag (`tag_numbers` draws 1027 for seed 2026). The generator now skips anchor numbers with a `while` loop that draws no random number, so the other generated numbers do not move.

## Learnings (proposed)
- A restricted document cannot be written to by the default writer after registration: `workflow._load` returns "no record" because `confidentiality.is_hidden` applies. Set the restriction last in a generator.
- The project's default revision scheme for P&IDs is numeric, so a ticket that says "revisions A and B" needs `revision_scheme="alpha"` on `RegisterDocument`.
- `ruff check` (E501 at 100 columns) is stricter than `ruff format`; run both on touched files.
