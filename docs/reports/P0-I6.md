## Outcome
Objective met: yes. People and agents post to a project feed; hashtags resolve to records, codes, signals, topics and mentions and never change a record; ledger
activity shows as aggregated event cards; an MCP agent proposes record changes that a person accepts from the CLI or the API; a seeded, deterministic simulated
team plays working days through the API and MCP, and `sim_assert` proves the suite holds what the team intended.
Demo `just demo P0-I6` ran clean on the final tree: a simulated day, the crew's posts in the CLI feed and in a remote TUI, the agent's proposal waiting in the
review queue, the agent refused with 403 `agent_must_propose`, a person accepting from the CLI, `sim_assert` green, and an identical ground-truth digest from the
same seed on a second empty ledger. The three workstream demos (`P0-I6-A`, `P0-I6-B`, `P0-I6-C`) also run clean.

## Cross-workstream decisions
D1 to D7 of the fanout plan stand. D4 became B15: an `agent:` token is refused on every record-changing command and file write (403 `agent_must_propose`), so the
simulator's role actors are `user:sim-<role>` and only the assistant is an agent. D5 as built: `effective_time` context variable, no change to `Command`, `Event`,
`Ledger` or `event_hash`. A direct-write MCP mode and per-role tool permissions were not built (human gate, ADR-0005).

## Learnings
Appended: L-P0-I6A-1 to 5, L-P0-I6B-1 to 7, L-P0-I6C-1 to 11. The ones that change how the next increment works: batch only independent tickets (A-5); a remote door takes

print a count with their singular (C-6).
