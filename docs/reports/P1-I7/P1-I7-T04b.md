## Deviations
Two small additions to the code the STEPS did not spell out; neither changes a signature, option, help text or printed line.
1. Imports: `cast` from `typing`, and `AutomationAccess` and `InboundAuth` from `tl_core.integration.contract` (the same module `service.py` imports them from). They are used to type `create`'s `--auth` and `--access` values as `cast(InboundAuth, auth)` and `cast(AutomationAccess, access)`. Without the cast, pyright strict fails with two `reportArgumentType` errors on the `str` values (see the first `just check` run below). The model still validates the values at run time, so a bad value is still refused by `service_errors()`.
2. `assert issued.secret is not None` in `create` and in `rotate-secret`, to narrow the `IssuedSecret | None` type before printing the secret. The ticket says `issued.secret` is not `None` for a new endpoint and a rotation; the assert only documents that.

## Learnings (proposed)
- pyright strict flags a CLI `str` passed to a pydantic command field typed as a `Literal` alias (`InboundAuth`, `AutomationAccess`). The STEPS do not mention it. The fix is a `cast` to the alias; the model validates at run time. Worth a line in the ticket template for any CLI option that maps to a Literal field.
- The `show` STEPS and the `ls` STEPS do not call `admin_gate`, while FANOUT D12 says the endpoint commands are admin commands. Implemented as the STEPS say. See the open question below.

## Open questions / Blocked
- Blocked: none.
- Open question for the supervisor: should `ls` and `show` run `admin_gate(ctx)` as well? FANOUT D12 says the endpoint commands are admin commands, and `create`, `mode`, `rotate-secret`, `enable` and `disable` gate. `ls` and `show` do not (their STEPS do not say to). Neither prints a secret, and the provided test does not cover a non-admin reader, so I did not add a gate.
