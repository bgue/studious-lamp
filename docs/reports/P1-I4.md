# Report — P1-I4 Cost snapshots (M11) and P6 XER schedule snapshots

Branch `p1/i4`. Plan: [docs/tickets/P1-I4/README.md](../tickets/P1-I4/README.md). Decision record: [ADR-0015](../adr/0015-cost-and-schedule-snapshots.md). Module pages: [schedule](../modules/schedule/README.md), [cost](../modules/cost/README.md). Runbooks: [schedule-snapshots](../runbooks/schedule-snapshots.md), [lake-sync](../runbooks/lake-sync.md), [simulator](../runbooks/simulator.md). Demo: `just demo P1-I4` (`dev/demos/P1-I4.sh`).

## Outcome
Objective met: yes. The suite mirrors a cost system (cost codes with a measure matrix, one snapshot per period) and reads P6 schedules from XER files: each upload is an immutable snapshot, validated, compared with the one before, published as the current schedule and linked to by stable activity id.

- **Cost (M11).** `tl cost import` previews (anyone signed in) and applies (admin) a period's CSV as one correlated batch; reads and two reports (budget against forecast per code and unit, the records with no cost code) over the CLI, the API and MCP read tools.
- **Schedule.** An XER file is read by a bounded, deterministic reader (`tl-xer`) in the ADR-0014 resource envelope; a worker builds the typed rows into operational `sched_*` tables; the comparison shows date shifts, float erosion, activities added and removed, logic changes, progress and critical-path movement; a record links to an activity by id and resolves to the current snapshot or, as of a number or a date, to an earlier one; publishing queues a state-derived job that flags the links of removed activities and restores them when the activity returns; a look-ahead and a float trend per activity.
- **Entry points.** CLI `tl xer` (define, upload, start, publish, void, link, worker, reconcile, ls, show, activities, activity, resolve, health, compare, look-ahead, trend, unscheduled) and `tl cost`; API routes and `ApiClient`; thirteen MCP read tools and the proposable `propose_publish_schedule_snapshot` (agents propose only); TUI `F12` with the comparison and activity screens.
- **Lake.** A second pass of `tl lake sync` loads the built snapshots: silver `schedule_snapshot` and `schedule_activity`, bronze `xer_<table>` (P6 tables) and `xer_other`, the mart `mart_float_trend`; a rebuild equals the incremental lake.
- **Simulator.** A planner actor (`schedule_updater`) sends the weekly XER files of `tl_xer.synth.series` and links the planner's records to activities through the public interfaces; `sim_assert` knows the schedule setup of controllers and workers as `operators`.

Demo path verified: `just demo P1-I4` passes its ten clauses on SQLite and on Postgres (see Showcase). Verified on a fresh clone: not repeated; the demo and the gates ran on the final tree of the `p1/i4` worktree.

## Security review
Three fresh-context reviews. The first (of c709ebe..27b2170) was changes-requested with ten findings; all are fixed (F1 1a47cba, F2 2b10c42, F3 a359254) and the re-review at b7e7ed5 confirmed each. The second left two MEDIUM and several LOW findings, fixed in a2154cb and d18d49b. The third (at bf361d1) confirmed the second round sound and left two MEDIUM, three LOW and four INFO items, fixed in f65ac0c, 676a224 and 5463d0e. Every fix has a test that fails when the fix is removed (each mutated and killed).

| Finding | Fix |
|---|---|
| Reader: rows, cell weight, typed text, dates, ids (first review) | Total rows and a weighted budget, typed text bounded by the file size, chunked raw bundle, dates as dates, ASCII digits (F1) |
| Flagging inside the publish command was unbounded | A queued state-derived job in runs of 500, `Schedule.OrphansChecked` (schema change approved), caps of 100 links per activity and 60 000 references, 31-day data-date allowance, settle checks its claim, JSON-per-chunk insert on Postgres, reconcile writes rows before queueing (F2) |
| MEDIUM: a client could pass as the module's flag by sending source `svc:schedule` | `svc:` is a reserved source prefix (API and proposals refuse it, walk test); the module also requires the flag event's actor to be its service |
| MEDIUM: two columns differing only by case built a Valid snapshot and stopped the lake sync for good | The reader refuses names that repeat ignoring case; the lake makes a table only for the P6 tables (others go to `xer_other`, long format; at most 300 columns); each snapshot's bronze load is its own transaction and a content failure is recorded in `_tl_xer_failed` and skipped |
| `sim_assert` operators exemption too broad | Allow-list of schedule-setup events, `schedule.*` records and `svc:schedule` link flags; file events must be on a record the log names; the report counts what was excused |
| `as_of` shaped like a date but not one raised 500 | Names nothing |
| A generic `AddLink` to an activity reference skipped the link cap | Generic `AddLink`/`SuggestLink` to a `schedule.ActivityRef` is refused (`MODULE_COMMAND_TARGETS`); `LinkActivity` is the way |
| Unbounded open snapshots | At most 20 waiting for a build per schedule (`too_many_open_snapshots`) |
| `schedule_detail` read every snapshot and made a query for each baseline | Paged (50, at most 200), baselines from one read of the published snapshots, constant query count (tested) |
| Postgres dialect SQL inside the module (AGENTS rule 5) | `tl_adapters.bulk.bulk_insert`, a parity test, and a test that the module holds no dialect SQL |
| Memory: a legal 48 MB file reached 938 MB, the wide-character variant was killed by the envelope | Rows are bounded by an estimate of their memory in bytes (420 million): worst legal file 583 MB; both variants are refused by the reader with a code (ADR-0015 section 2) |
| INFO: P6 "1900 = no date" | Stated in ADR-0015: refused as `bad_date` |

Round 3:

## Deviations from plan
- T04, T05, T11 and T12 were planned as Haiku tickets and were taken over (reasons in the table). T09 was split into T09a1 to a3 and T09b/T09c so each ticket changes one file.
- Added to the plan: S7 to S10 (API, CLI operations, TUI client interface, MCP proposal), S11 (`reconcile`), S12 (reports and TUI text helpers), S13 (lake loader and the weekly series generator), S15 (simulator).
- `Schedule.OrphansChecked` and the `orphan_check_queued` payload field changed an unmerged schema after the first review; approved as additive and pre-release (APPROVALS 2b10c42).
- A generic link to an activity reference is refused (the reviewer asked for a cap hook; refusing is the stronger form and `LinkActivity` already does the work).
- The lake tables `schedule_snapshot`, `schedule_activity` and `mart_float_trend` gained a `scope` column (round 3). A lake made earlier loads its schedule snapshots again at the next sync; nothing is migrated.
- The bronze load of a snapshot is a lake transaction of its own, so the line `in snapshot S` of `tl lake sync` names the last lake snapshot (4 for the demo's two snapshots, not 2).

## Escalations and decisions
- The reserved source prefix `svc:` is an edit of `tl_core.services.reserved`; P1-I7 adds prefixes on another branch, so the edit is one more tuple entry (additive).
- `sim_assert` now excuses declared operators for schedule setup only. This loosens a safety check by design and was marked for orchestrator review.
- ADR-0015 accepted 2026-10-17; no further ADR was needed.
