# P2-PTW-S5 report: the lapse job

Deviations: none outside Allowed paths. The spec's `docs/reports/P2-PTW/S5.md` path is used as written.
Two small additions inside the allowed files: `permit_world.active_many(n, valid_until)` (append; bulk Active permits
through ledger events for the limit test) and a boundary test `test_a_permit_is_lapsed_at_the_very_instant_its_validity_ends`
(added after a mutant survived).

## Registration seam
The scaffold job has no registry or entry point: callers pass `[LapseKind()]` to `JobRunner` (as `p2/i4b` tests, demo and
accept script do). Nothing outside `packages/tl-modules/permits/` was needed. No worker or scheduler is wired and there is no
CLI command: a later ticket wires them. `run_once` is the entry for tests, the accept script and `dev/demos/P2-PTW.sh`.

## Re-queue id
Same run id: `ptwlapse:<project>:<minute>` is queued again (UPDATE done -> queued, in the settle transaction, where the
queue row is already done). The flagged permits no longer match, so the second pass takes the next 500. It happens only when
`remaining > 0`, so a run that fits writes no re-queue. `request()` stays False for a queued or done id.

## Feed policy
`feed_policy = "none"`: the S1 schema (`PermitLapsedPayload`) fixes it to `none` ("permits make no feed card here").
Payload: `record_id`, `valid_until` (the one that passed; null end -> null), `at` = the minute of `now`, `feed_policy`.
Review fix: a permit with a NULL `valid_until` is never selected (SQL `IS NOT NULL`, None skipped), so it is not re-flagged each run.
PG limit test uses LIMIT=3 (seed 4); sqlite keeps 501.
