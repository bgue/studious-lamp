branch `p0/i4b-t20-fs-object-store` was used as the task instructed (not a deviation). Three choices inside the spec wording,
listed so the reviewer can check them:
1. The "already present" test for a content key uses `Path.is_file()`, not `exists()`. A directory at a content-key path
   therefore raises `IsADirectoryError` instead of being reported as stored. Confirmed by probe: no error is swallowed and
   `.tmp` is left empty.
2. The parent directory is fsynced only after an `os.replace`. When a content key already exists and the new bytes are
   discarded, there is nothing to make durable, so no directory fsync is done.
3. `redeem` requires exactly one `op`, one `exp` and one `sig` parameter. A repeated parameter is treated as malformed
   (`PresignInvalid`).

## Learnings (proposed)
- `tempfile.mkstemp` creates files with mode `0600`, so every object stored by `FsObjectStore` is owner-only. The ticket does
  not mention file mode. If other local users or processes must read objects, the supervisor needs to decide on a `chmod`
  (for example to `0644` before `os.replace`). Not changed here.
- The ticket asks for `put_via_url` to "always replace", which for a content key (`sha256/...`) overwrites an existing
  object. See the first open question. A ticket that says "a content key is never replaced" for `put` but "always replacing"
  for `put_via_url` should say which rule wins.

## Open questions / Blocked
- **Immutability of content keys through `put_via_url` (needs a supervisor decision).** The ticket says `put_via_url`
  writes "always replacing", and the module contract says "a content key is never replaced" (brief §5.2). Both cannot hold
  for a `sha256/...` key. I implemented the ticket literally: a valid `put` URL for a content key replaces the existing
  object. Probe result: a content object holding `abc` was overwritten with `tampered` through `put_via_url`. This only
  matters if the upload service issues `put` URLs for content keys. Options: (a) refuse content keys in `put_via_url`
  (for example, raise `PresignInvalid` when `is_content_key(key)`), or (b) keep the literal behaviour and document that
  callers must only issue `put` URLs for `staging/...` keys. I did not choose between them, because it is an immutability
  decision.
- No other open questions. Status is done; nothing was blocked.
