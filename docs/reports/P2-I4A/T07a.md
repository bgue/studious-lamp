## tui-layout checklist
1. Glance: breadcrumb and log name the place; the panel and screen show key · subject, then the state line.
2. Identity line first; the kind fields are `Label  value`; the work order line is the only unlabeled value, under its heading.
3. Sections Detail, Work order, Technical (technical only), named, one blank line apart (layout renderer).
4. Everyday facts sit in the summary line; kind fields in Detail; the id only in Technical.
5. Log columns: Number, Subject, Kind, State (ticket order, see deviation 6); constant columns hidden by the log's rule.
6. Empty values: `—` in cells; Detail note `No details`; Work order note `none yet`.
7. Works at 80 and 170 columns: tested in test_mounts_at_80_and_170_without_overflow.

## Learnings (proposed)
- `humanize("uom")` gives `Uom`, so a requisition field named by its code reads badly in Detail. A label map for kind fields may be wanted; the ticket does not name one.
- `RecordNotFoundError` is a `ServiceError`, so it is in `CLIENT_ERRORS` and the screens' existing catch covers it. No extra handling was needed.
- `FakeClient` already mixes in the requisition fakes (`_init_requisitions`), so `seed_requisitions(FakeClient())` is enough for a pilot test.

## Open questions / Blocked
- The log calls `list_requisitions(project)` with the default limit (200). `RequisitionList.total` is the number of rows returned, not the true count, so a project with more than 200 requisitions would show a truncated list and a wrong total with no warning. Should the log page or raise the limit (the module's MAX_LIMIT is 500)?
