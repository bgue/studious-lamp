## Learnings (proposed)
- `re.IGNORECASE` without `re.ASCII` folds the Kelvin sign (U+212A) onto `k`, so `find_item_numbers("P123-CKR-0042", "P123", ("CKR",))` returns `["P123-CKR-0042"]`. Identifier patterns applied to untrusted text may want `re.ASCII` as well. The STEPS say `re.IGNORECASE` only, so this was left as written (see Open questions).
- `normalise_subject` bounds the input to `MAX_SUBJECT_CHARS` before NFKC, but NFKC can expand characters. Input of 500 `U+FDFA` gives a 9000-character result, so the output bound is not `MAX_SUBJECT_CHARS`. The provided test only uses ASCII and does not catch this.

## Open questions / Blocked
none blocking. Two questions for the supervisor, neither changes the test result:
1. Should `find_item_numbers` use `re.IGNORECASE | re.ASCII` so that a Unicode case-fold (for example the Kelvin sign for `K`) cannot produce an item number? The STEPS do not say; I did not change the pattern.
2. Should `normalise_subject` cap the output at `MAX_SUBJECT_CHARS` after NFKC (for example by a final `[:MAX_SUBJECT_CHARS]`), since the docstring says the bound applies to the text? The STEPS do not say; I did not change it.
