## Learnings (proposed)
- Textual's `Select` delivers `Select.Changed` through the message queue (`textual/widgets/_select.py`, `_watch_value` calls `post_message`). A flag set around a programmatic `select.value = ...` is cleared before the handler runs, so the flag never suppresses the event. Use "last value the picker set" and compare `event.value` with it instead.
- `InvalidSelectValueError` is importable from `textual.widgets.select` and is what Textual raises for an unknown `Select` value.
- Every fake record in `fakes.py` has type `core.Record`, so no provided test exercises a type-dependent default relation. A fixture with a second record type would have caught item 1 below.

## Open questions / Blocked
1. **Relation does not follow the highlighted record (ticket defect, not implemented around).** `on_select_changed` sets `_manual_relation = True` on any `Select.Changed`. Because the `Changed` event is delivered after `_setting_relation` has gone back to False, the picker's own programmatic `_set_relation` call also sets it. The probe shows `_manual_relation` is True right after mount, so `_on_highlight` never changes the relation again. Effect: the relation is pre-selected only from the first source type and the type of the record that is highlighted at mount; it does not follow the highlighted row. The provided tests pass because every fake record is `core.Record`. Proposed fix for the supervisor to decide (I have not applied it, since the ticket prescribes this mechanism and forbids redesign): in `_set_relation`, store `self._auto_relation = code` before assigning; in `on_select_changed`, set `_manual_relation = True` only when `event.value != self._auto_relation`. Trade-off: choosing, by hand, the same relation the picker would pick does not lock it. The ticket owner should decide whether to amend the ticket or accept the current behaviour.
2. No other open questions. Status is `done` on the ticket's own acceptance criteria; item 1 is a spec question for review before merge.
