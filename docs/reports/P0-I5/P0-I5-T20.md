## Learnings (proposed)
- Ruff B905 (`zip()` without `strict=`) fires on the common pairwise idiom `zip(xs, xs[1:])`, and `strict=True` is wrong there because the lengths differ on purpose. Use a set-size or index-based check for adjacent duplicates. The ticket's "run `uv run ruff format` before committing" does not catch lint failures, so `just check` should be run before committing.
- The provided tests and the ticket's specification agree on every point I checked (channel, operation, message, headers, example, determinism, duplicate refusal). No test contradicts the spec.

## Open questions / Blocked
none that block this ticket. One question for the supervisor, not a blocker:

- Operation keys are `"receive" + event_type.replace(".", "")`, as the spec says. Two distinct event types whose dots fall in different places (for example `A.BC` and `AB.C`) would produce the same operation key `receiveABC`. The second one in sorted order silently overwrites the first in `operations`, and the spec does not say what to do. I did not add a check, because the ticket does not define it. Should the generator refuse such collisions, or is this name space guaranteed not to occur?
