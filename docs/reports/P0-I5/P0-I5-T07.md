## Raw SQL changed
- `test_reconcile.py`, module-level `INSERT INTO cur_files`: `:status, 0, 'user:t'` → `:status, FALSE, 'user:t'`, because `deduplicated` is boolean and Postgres rejects integer `0`.
- `test_reconcile_races.py`, inline `INSERT INTO cur_files`: `'available', 0, 'user:t'` → `'available', FALSE, 'user:t'`, for the same reason.

The other statements already used `text()` with `:name` binds and full ISO timestamps. The `1, 1` integers in the `VALUES` list are `version` and `last_seq`, not booleans, and were left alone. No `?` placeholders, `sqlite_master`, `PRAGMA`, `rowid`, or `get_columns` appear in the three files.

## Learnings (proposed)
- `ruff check --fix` on the converted files reported one E501 (a `def` line that became 103 characters once `DbTarget` was added). `ruff format` fixed it and the subsequent `ruff check` was clean. The ticket's recipe runs `check --fix` and does not mention format before check, so run format before the final check.
- `tl_adapters.db.make_ledger` is annotated to return `Any`. A fixture annotated `Iterator[AppendInLedger]` type-checks under pyright without a cast, so the ticket's `AppendInLedger` annotation works as written.
- The Postgres run of these three files takes about 50 s against about 5 s on SQLite. Most of the difference is in the poller tests in `test_changefeed_integration.py`, which wait on real timers. That is timing, not a failure, and the ticket says not to change it.
- After the Edit and sed steps the harness printed "changed on disk since you last read it" and "modified 1 file you've previously read" for files this session had just edited itself. Both were the session's own writes, not outside changes.
