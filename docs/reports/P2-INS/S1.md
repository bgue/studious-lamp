## Facts for the review
- `subject_id` per kind: record, file (record of the file), thread (`record_id`), numbering, IWP/readiness events = the record id;
  link = the `from` record (to-end links found via `cur_links.to_id` + link stream); constraint = the constraint id (via
  `cur_core_constraint.subject_id`); proposal = the proposal id (via `cur_proposals`). Thread events need no `stream_id` match.
- `cur_proposals` column is `command_json` (spec says `command`); matched with `CAST(command_json AS TEXT) LIKE ... ESCAPE`.
- Statement count N = 15 (1 record, 3 id lookups, 1 far-end read, 1 own candidates, 1 ledger read, 7 stream filter, 1 payload ids);
  16 when a linked record has related candidates; unchanged for 250 -> 500 own events, 20 -> 40 links, 10 -> 20 proposals, limit 200.
- `confidentiality.filter_events` costs one statement per scanned-stream event (threads, proposals), so `_visible` does the same
  test in a batch (`hidden_event_streams` + one `hidden_among` over all ids); a test equals it to `filter_events` for the five viewers.
- Pages may be short when the 30-related-row quota or the 1000-candidate cap ends them; the cursor is lossless (tests).
- Guards (activity.py): hidden record 251; cursor strict 187/222; both link ends 199-200; allow-list 34; caps 42-45, 263, 286; `_visible` 279.
