## Learnings (proposed)
- The provided statement-count test sees `BEGIN DEFERRED` as a statement. The SQLite engine's `begin` hook (`packages/tl-adapters/src/tl_adapters/sqlite/engine.py`, `_on_begin`) runs it through `exec_driver_sql`, and `before_cursor_execute` reports it. Any single read through a SQLAlchemy connection therefore counts as two. `tl_core.readiness.harness` counts writes only, so the contract harness is not affected.
- Editing an entry-point line in a package's `pyproject.toml` does not take effect until `uv sync --all-packages` runs again. The first gate run used the stale entry points.

## Open questions / Blocked
Blocked on `test_the_check_runs_a_fixed_number_of_statements[sqlite]`, which asserts `len(seen) <= 1`. The check's one SELECT is preceded by the adapter's `BEGIN DEFERRED`, so `seen` has two entries (`['BEGIN DEFERRED', 'SELECT cr.id, ...']`). Any SQLAlchemy read on a fresh SQLite connection produces the same two entries, so I could not satisfy the assertion without bypassing the connection, and I did not edit the test. The Postgres run has no `BEGIN` line and the Postgres parametrisation passes.
Question for the supervisor: should the assertion count only statements that are not transaction starts (for example, drop `BEGIN` lines), or should the check be accepted as-is on the Postgres run only? The ticket must be decided before this is merged.
