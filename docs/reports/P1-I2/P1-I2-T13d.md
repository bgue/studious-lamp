## Deviations
Two small deviations inside Allowed paths, both to satisfy pyright and to keep validation errors on screen:
- The stub's import list was extended: `cast` (typing), `Selection` (`textual.widgets.selection_list`) and `Purpose` (`tl_mod_documents.handlers.transmittals`) are imported at module level, because `on_mount` needs `Selection` and the `purpose` cast needs `Purpose`.
- `action_create` builds the `Recipient` list inside the same `try` as `CreateTransmittal` and the send (the ticket's STEPS build it before the `try`). An empty recipient name such as `:Acme` is a `ValidationError` from `Recipient`; outside the `try` it would crash the screen instead of showing in `#tc-status`. The purpose is passed as `cast(Purpose, purpose)`: pyright (standard) rejects a `str` for the `Literal` field. The cast is type-only; the model still refuses a bad purpose at runtime, which the test `test_a_missing_field_is_shown_and_the_composer_stays_open` checks.

## Learnings (proposed)
- A `str` read from an `Input` cannot be passed to a pydantic field typed as a `Literal` (e.g. `Purpose`) under pyright standard; the code needs a type-only `cast(Purpose, value)` and the runtime check stays in the model. Worth a line for any TUI form that builds a command with a literal-typed field.
- `ruff format` does not sort imports; a new first-party import group needs `ruff check` (I001) to pass. Running `just check` before committing catches it.
- Editing a file with a script (python heredoc) made the harness report the file as "modified since read"; it was my own change, not an external one.
