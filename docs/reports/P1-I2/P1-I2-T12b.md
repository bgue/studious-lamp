## Deviations
One deliberate departure from the STEPS text, inside the ticket's scope. Step 2 says "a header name that appears twice" is a file error. I filtered out blank header cells before the duplicate check (`if name and header.count(name) > 1`), the same way the sibling `tl_mod_engineering/imports/mapping.py` does. Reason: an export with a trailing comma in its header has two blank header cells, and the literal reading would reject the whole file with the message "the file has a column twice: " (empty name). A blank header names no column, so it cannot be a repeated column. A one-line comment in the code records this. If the supervisor wants the literal STEPS behaviour, the change is one line and no test covers either choice.

## Learnings (proposed)
- The ticket names the engineering sibling as `packages/tl-modules/engineering/src/tl_mod_engineering/import_/mapping.py` in Context. The real path is `tl_mod_engineering/imports/mapping.py` (no underscore). It was found with a directory listing; the ticket's path does not exist.
- The ticket says the test "compares [the messages] exactly". The provided test uses `pytest.raises(..., match=...)`, which is a regex `search`, not equality. Messages are matched as substrings or regexes, and the `r"the file lacks the column\(s\): NAME"` pattern shows the author expected that. An implementer following "exactly" literally could over-constrain the message.
- The pasted `model.py` in the ticket reads `import annotationsfrom dataclasses import ...`. That is a paste artifact; the file on disk is correct. Read the file, not the paste.
- Acceptance says "8 test functions pass (on SQLite and again on Postgres)". Pytest reports 19 cases, and the adapter option does not change that count for non-database tests. The "8" is the function count, not the case count.
- `pytest.raises(match=...)` in the test for the template error `columns.0.to` relies on the pydantic `loc` joined with dots. This works because the location is a list index, `str(part)` makes it `0`.
