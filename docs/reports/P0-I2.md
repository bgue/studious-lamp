## Deviations from plan
Decisions B1 to B16 are in `docs/tickets/P0-I2/README-B.md`. The ones a reader must know:
- **Contract change (orchestrator-approved, B7):** `ClientInterface.list_records` gained an optional `order_by`, and `tl_core.services.queries.list_records` an allow-listed, validated `order_by` (empty values last, `id` tiebreak). Sorting on pset columns waits for the query language (P0-I4).
- **Additions to P0-I1 code (B1):** `get_record_by_id`, `record_history` and optional `record_type`, `limit`, `offset`, all additive.
- **§15 performance gap:** the grid is virtualised and the first page and a server-side sort are one `LIMIT` query, but "load everything" is capped (End loads at most 5,000 rows in a worker; Ctrl+A selects loaded rows only and says so). The brief's target of under 150 ms to 100k rows is not demonstrated; real windowed paging and filters arrive with the query language (P0-I4).
- **A save is not atomic (B16, orchestrator ruling):** `forms.py` sends an `UpdateRecord` and then one `SetPsetValues` per (pset, layer); a partial save is possible and is reported. Follow-up `docs/tickets/P0-I3/T00-atomic-edit-command.md`.
- **Ticket splits and supervisor-built pieces:** the shell skeleton, grid core, `forms.py` and the demo were built by the supervisor; the other pieces were tickets with supervisor-provided tests stored under `docs/tickets/P0-I2/provided/` and confirmed satisfiable by a discarded reference implementation.
- `tl-tui` now depends on `tl-schema` and `tl-adapters` (only `embedded.py` and `main.py` import the latter).

## Escalations and decisions
- Orchestrator rulings: server-side sort and the End worker (B7 to B9); `None` in `SetPsetValues.values` means "unset this property" (B15, A20); a non-atomic save is acceptable for Phase 0 (B16).
- Supervisor-pieces review (73bb88c) requested changes: the load-all freeze (fixed by B7 and B8), a failed page fetch that marked the list complete (B12), `OFFSET` without `LIMIT` (portable `LIMIT`), TSV exporting symbols (raw values now). Verification then found a race between cursor paging and the End worker that duplicated rows (fixed, B13, regression test).
- No unresolved *Blocked* entries.

- **Open product question:** should values in a `locked` pset be non-clearable? Today clearing is a data edit and shows as nonconformant (A22). Also, clearing the last value of an optional pset hides its missing required properties because a pset is engaged only while it holds a value (A4, A22).
- P0-I4: remote `ClientInterface`; real windowed paging and sorting on pset columns with the query language; keep records validating against the schema they were opened with (`effective_by_hash`, A's follow-up); live row highlight and conflict banner.
