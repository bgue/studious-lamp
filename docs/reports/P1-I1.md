## Outcome
Objective met: yes. The `engineering` module is the first module of Phase 1 and sets the shape of the next ones.
- **The module seam (ADR-0010).** A module record is a row of `cur_core_record` plus a row of the module's own table; modules are found through the entry point `throughline.modules` and a `ModuleSpec` (record types, projectors, class-bound psets, numbering patterns, and the generic commands a type allows). Generators read `schema/modules/<m>/module.yaml`. A class can bind property sets without touching the effective schema or its hash.
- **The standards registry.** Code lists with `value_list_policy` and crosswalks, mnemonics, numbering patterns and units, loaded idempotently from one YAML edition (`tl standards load`), versioned, closed rather than rewritten.
- **Tag and TagClass.** Tag numbers are parsed into typed segments against the registry pattern, every problem listed at once; the class makes property sets mandatory (`class_required`); rename, split and merge supersede with links; a workflow guards the move on while psets are missing.
- **Entry points.** CLI (`tl standards`, `tl standards class`, `tl tag`, `tl tag import`, `tl tag report`), API (14 commands, 7 reads, 21 error rows), TUI tag register (`F8`), MCP read tools, a simulator tag clerk, and a legacy instrument-index mapping template with a sample file.
- **Security.** A fresh-context review of the HTTP commands found one HIGH (a user could change registry records through the generic `UpdateRecord`), two MEDIUM (a client could set `origin` and skip the numbering pattern; no request-size bound on `/commands/`) and three LOW. All were fixed with tests and the re-review passed.

## Deviations from plan
- The plan listed the legacy mapping template as part of T12 and an `after-t09c` set of tests; the template, sample file and end-to-end test were built by the supervisor, and two tests waited for tickets in flight (T09c, T12) before they were added.
- The class-binding allow-list of the ADR addendum says which generic commands a module record type allows, not who may run them: core services see an actor string, not a role. A command that needs a role is a module command behind `admin.command.<Name>` or `require_admin`.
- The API offers no `SplitTag` (the command table answers with one result); use `tl tag split`.
- The wide per-type view `v_<module>_<class>` that ADR-0010's acceptance names as a condition is **not built**: no consumer needing a flat per-type row exists yet (the P1-I8 lake marts are the first). Module code that joins `cur_core_record` and its table does so in `registry.py` and `reports.py` only, for its own reads. See follow-ups.

## Escalations and decisions
- ADR-0010 proposed, accepted by the orchestrator under ADR-0008 decision 6; its addendum (generic commands on module records, source-end link check, server-set `origin`, `RecordTag` admin-only) accepted after the security review.
- Rulings: `tl tag import --apply` is admin-only (preview open); a user may link to a registry record as the target (documented design); the uncapped admin-only fields (pattern segment contents, templates, ITR templates, nested pset values) are acceptable behind the 1 MiB request limit.
- Schema approvals: see `docs/reports/APPROVALS.md` (module schema and `tl:record_types`, the standards fixture, the `engineering-tag` workflow fixture, the `superseded_by` slot).
