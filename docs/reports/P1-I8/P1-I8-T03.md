## Learnings (proposed)
- STEP 6 of the ticket says a pset is found by "the second dot-separated part of the path". That is wrong for pset names that contain a dot. `schema/core/psets.yaml` and `packages/tl-schema/src/tl_schema/effective.py` (line 80) both name `prj.shutdown_tie_in` as a valid pset name. For a path such as `psets.prj.shutdown_tie_in.size`, the second part is `prj`, which matches no pset, so the `mcp_schemas` entries for that pset are dropped without any error. A ticket that writes a path-parsing rule should say to resolve the pset by longest-prefix match, as `tl_schema.effective.resolve_path` does, or by carrying the pset name from the property walk in `_properties`.
- The stub and STEP 8 say `old_hash=old.hash or None when old is None`. That is ambiguous. I implemented `old.hash if old is not None else None`, which is the stub's own expression and what the provided test expects.
- A first `uv sync --all-packages` prints a `UV_NATIVE_TLS` deprecation warning. It is harmless, and the `just check` run was unaffected.
