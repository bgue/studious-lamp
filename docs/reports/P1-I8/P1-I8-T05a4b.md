## Learnings (proposed)
- `registry.list_packages` defaults to `scope=None` (all scopes). Project-kind packages (`project:<id>`, e.g. `schema/fixtures/prj.P123@1.0.0.yaml`) are published by the same handler, so they are exported too unless a scope is passed.
- `list_packages` silently caps each state at `MAX_PAGE` (1000) rows; an export beyond that would be partial with no message.
- The provided test does not cover a `--package` filter that matches a package with several versions in two scopes.

## Open questions / Blocked
1. **Scope (for supervisor decision; not changed).** The STEPS call `list_packages` without `scope`, so a published project-scoped package would be written into the company export. If two scopes publish the same `<package>@<version>`, both rows map to one file name; the check phase sees no file yet, so the second `_write_atomic` silently replaces the first and both print `wrote`. Should the export pass `scope="company"` (the brief says the company keeps its schema in git), or is all-scope intended? I followed the STEPS literally.
2. `version_tuple` in the sort is outside `service_errors()`; it raises `ValueError` on a malformed stored version. Registry-validated, so low risk; left as the STEPS say.
