# ADR-0015 — M11: cost snapshots and P6 schedule snapshots

Status: accepted 2026-10-17 by the orchestrator under ADR-0008 decision 6 (proposed by the P1-I4 supervisor)
Date: 2026-10-17
Deciders: P1-I4 supervisor (proposal); accepted by the orchestrator
Brief sections: §9 M11, §7.2 and §7.3 (links by stable id, orphans), §9 M1 (derivation, shared with ADR-0014), §28 (lake bronze and silver), §8 and §18 (access, agents propose)

## Context
P1-I4 builds M11: a mirror of the cost system's codes with period snapshots, and P6 schedules read from XER files, each upload an immutable snapshot, compared with the one before, published as the current schedule, and linked to by stable activity id.

An XER file is **untrusted input** from a person's tool, as the PDF and spreadsheet extractors of P1-I3 were. Everything P1-I3 learned about those readers applies (L-P1-I3B-1 to 8, L-P1-I3-10): bound every dimension and refuse instead of cutting, no clock, no unpickling, fixed messages, the resource envelope of ADR-0014.

## Decision

### 1. Two modules, `cost` and `schedule`
Module name equals record-type prefix (ADR-0010), so M11 is two modules. Record types:

| Type | Key | Notes |
|---|---|---|
| `cost.CostCode` | the code (`4210-PIP-WLD`) | hierarchy, unit of measure, and the latest measure matrix: {hours, quantity, amount} x {budget, actual, earned, forecast to complete, estimate at completion} with the period and the as-of date |
| `cost.CostSnapshot` | `<period>@<revision>` (`2026-09@1`) | one imported period; a corrected file is the next revision |
| `schedule.Schedule` | its code (`MAIN`) | the series of snapshots of one P6 project; points at the current snapshot |
| `schedule.ScheduleSnapshot` | `<schedule>#<n>` (`MAIN#2`) | one XER upload; also the **job record** of its build |
| `schedule.ActivityRef` | `<schedule>/<activity id>` (`MAIN/A1230`) | the stable target of links to one activity |

Figures per cost code per snapshot are kept (`cur_cost_snapshot_value`), so a report can say what the matrix was in an earlier period. A late snapshot (an earlier as-of date) adds history and leaves the matrix of a later one alone.

### 2. Reading an XER file (`packages/tl-xer`)
The reader is pure Python (stdlib only; no PyPI XER library is used, so no new licence). It is a security-reviewed parser of untrusted input:

- **Refuse, never cut.** Bytes (50 MiB), tables (300), columns (200), rows per table (400 000), **rows over all tables (1 200 000)**, a **weighted cell budget (20 million; a row weighs its columns and at least 16, so millions of one-column rows cannot pass as a few cells)**, characters per field (32 000), and the typed rows (60 000 activities, 200 000 relationships, 60 000 WBS nodes, 2 000 calendars, 300 000 codes, 300 000 user field values) are bounds; a file over any is refused with a fixed code. A tab count is taken before a line is split. **The text of the typed rows is bounded too: at most twice the size of the file plus 16 MiB, in bytes (a code or a user field is copied into every row that links it, so a few megabytes of links could name hundreds of megabytes of text); past it the snapshot is Invalid with a report (`typed_too_large`), not a crash.** Dates must lie in 1990 to 2100 and are written with explicit widths; digits are ASCII digits.
- **Encoding is decided once.** UTF-16 is refused; a UTF-8 byte-order mark or valid UTF-8 means UTF-8; plain ASCII is ASCII; anything else is Windows-1252 (what P6 writes by default); a byte Windows-1252 leaves undefined is refused. NUL, other control characters, line and paragraph separators and text-direction marks refuse the file (a NUL crashes Postgres, a mark spoofs a screen).
- **No clock, no state.** The same bytes give the same result, byte for byte (`process` is a pure function; the gzip of the raw bundle carries no time stamp).
- **Runs in the D9 envelope** (`tl_core.derivation.envelope.run_in_envelope`): a child process with a scrubbed environment, address-space and CPU limits and a wall clock. The answer is three frames (metadata JSON, typed snapshot JSON, gzip bytes) and **nothing is unpickled**. The parent does not believe the child: lengths, the report's fields, the SHA-256 of the typed frame, every cell of every typed row against its column kind (and, for text, against the characters the reader refused), and the inflated hash of the raw bundle are checked before a result exists (`tl_xer.wire`). The answer is read from views of the payload (no slices), the typed frame is parsed once, and the bound on the answer follows the size of the file (`limits.answer_bound`: three times the file plus 72 MiB, never more than 222 MiB). The raw bundle is inflated in chunks of 64 KiB with every byte counted and a bound on the length of any one line (a gigabyte of zeros is one line to a line iterator). A breach, a crash, a recursion or memory error or a malformed answer is `XerLimitError` with fixed text.
- **Messages are fixed text.** The only values in them are table and column names that passed a name pattern, activity ids that passed the id check, project names that passed the length check, and counts. No path, no cell, no exception text.
- **Measured** (the envelope's limits are 60 s and 1 GiB; the target is a third of the clock and well under the memory): the worst legal file, the typed maximum (60 000 activities, 200 000 relationships, 300 000 codes, 300 000 user fields; 42.6 MB), reads in **16.8 s with 582 MB in the child and 573 MB in the parent**; 3 tables of 390 000 rows of 16 fields (42.5 MB, 18.8 million weighted cells) 7.7 s and 283 MB; 4 tables of 310 000 one-column rows 3.7 s and 112 MB; 98 000 user fields of 470 characters (52.1 MB) 6.0 s and 307 MB. The file the security review used (14 one-column tables of 399 000 rows, 44.7 MB), which took 45 s and 649 MB before the total-rows bound, is refused in 3 s. The speed-ups: the raw bundle writes one JSON line per batch of rows (version 2 of the bundle) instead of one per row, the typed JSON shares the rows instead of copying them, and the child drops the typed rows before it writes the bundle.

### 3. The XER document schema (validation)
`tl_xer.typed.analyse` checks, and reports with codes (`error` blocks the snapshot, `warning` does not): a supported P6 version (8.x to 30.x); the tables `PROJECT`, `PROJWBS`, `CALENDAR`, `TASK`, `TASKPRED` and their required columns; **one project**: a file with several needs the one to read named (`Schedule.p6_project` or the snapshot's option), a named project the file lacks is an error, relationships to other projects are left out with a warning; a data date (`last_recalc_date`); unique non-empty activity ids of at most 60 characters (ASCII letters, digits and the punctuation P6 allows); dates written `YYYY-MM-DD HH:MM`, real, in the years 1990 to 2100, with ASCII digits only (other scripts' digits are refused, so no date or number can be read two ways); plain decimal numbers; known task types and statuses; every reference resolving (WBS, calendar, predecessor); a WBS tree with no loop, at most 100 deep and with no path over 500 characters. Optional tables (activity codes, user fields) missing or partial are warnings. The typed rows are activities, relationships, WBS, calendars, activity codes and user fields; every other table lives in the raw bundle only.

Units: durations and floats are hours as P6 writes them; a day is the activity's calendar `day_hr` (8 when unknown). Dates are ISO local date-times without a zone. `critical` means total float zero or less and not complete.

### 4. A snapshot is a job and its rows are operational tables
- **The build is a job** in the ADR-0014 queue (`job_queue`, kind `schedule.build`); the **job id is the snapshot's id** and the snapshot is the job record, so its attempts are events on its own stream (`BuildStarted`, `BuildFailed`, then `Built` or `Rejected`). A worker (`tl xer worker`) claims for **600 seconds** (`BUILD_LEASE_S`: the envelope's clock plus the settle, with a wide margin), reads the file in the envelope, and settles in one transaction **that first checks the claim is still the worker's** (a worker whose lease ran out writes nothing). The settle time at the limits was measured: **25 s on Postgres and about 13 s on SQLite** for the maximum typed snapshot (60 000 activities, 200 000 relationships, 300 000 codes and 300 000 user field values). On Postgres the rows go in as one bound JSON text per chunk of 20 000 rows and `json_array_elements` with casts (the pure-Python driver sends one round trip per row with `executemany`: 535 s for the same snapshot); SQLite uses `executemany` in chunks of 5 000. A merely bad file is not a failed job: the snapshot is `Invalid` and its report says why. A breach of the envelope fails the job for good and leaves the snapshot `Invalid` (FANOUT D9).
- **Workflow** `schedule.schedule-snapshot`: Uploaded, Processing, Invalid or Valid, Published, Superseded, Void. Moves are made by the module's commands and the job, never by the generic `TransitionWorkflow`.
- **The typed rows are operational tables** (`sched_activity`, `sched_relationship`, `sched_wbs`, `sched_calendar`, `sched_activity_code`, `sched_udf_value`), like `job_queue`: no event produces them, a projection rebuild never clears them, the archive and webhooks never read them. 20 000 activities of up to 100 columns would make events of megabytes (ADR-0014 alternatives); the ledger holds the facts (`Built`: counts and the SHA-256 of the canonical typed rows) and the rows come from the source file. After a restore `tl xer reconcile` reads the source file again, checks the typed hash against the one recorded and writes the rows. Until then every read of a built snapshot (activities, comparison, look-ahead, resolution, float trend, a record's activity links) is refused with `typed_rows_missing` (409) and says to run `tl xer reconcile`: an empty answer would show an empty comparison, call every activity gone and, in the flagging job, flag every link. The rows of a snapshot are written once and never updated: a snapshot is immutable.
- **Bronze** is the verbatim tables of the file, every one, as gzip-compressed JSON lines in the slot `raw` of the snapshot (SHA-256 of the uncompressed text recorded). **The lake loads them in a second pass of `tl lake sync`** (`tl_lake.xer`, because the typed rows are not events and the seq-driven sync cannot carry them): bronze `xer_<table>` (every field as text, with `_snapshot_id` and `_row_no`), silver `schedule_snapshot` and `schedule_activity` (floats in days of the activity's own calendar) and the mart `mart_float_trend`. A snapshot is loaded once and only a snapshot that stops being built (a Valid one that is voided) is taken out again, so a rebuild equals the incremental lake; one whose typed rows are not in the ledger yet (after a restore) waits for `tl xer reconcile`, and without an object store the bronze tables wait. The plan's "Parquet via the lake bronze loader" is met by the lake: DuckLake writes the Parquet files, the ledger path writes none and needs no `pyarrow`, which is not locked.

### 5. Links by stable activity id (brief 7.2, 7.3)
A record links to an activity with `LinkActivity`, which makes the **reference record** `schedule.ActivityRef` for `<schedule>/<activity id>` the first time and then the core `AddLink` (relation `references`, the activity told by the type of the target). A link is **floating** (resolves to the current snapshot) or **pinned to a snapshot number** (resolves to that snapshot). `resolver.resolve_activity(..., as_of)` reads the activity of the current snapshot, of a numbered snapshot, or of the latest published snapshot on or before a date; only Published and Superseded snapshots are history. Publishing a snapshot checks every reference of the schedule against it: a reference whose activity is gone is marked absent and its active links are **flagged stale** with a fixed reason (`activity is not in the published snapshot`), one whose activity is back is marked present and the links *this module* flagged are **restored** (`Link.Repinned`); a link a person flagged stays flagged. A link to an activity absent from the current snapshot cannot be made.

**Flagging is a queued job, not part of the publish command.** Publishing makes the snapshot current, appends `ScheduleSnapshot.MadeCurrent` (and `Schedule.SnapshotPublished`) saying whether a check was queued (`orphan_check_queued`: true when the schedule has any activity reference) and queues one job of kind `schedule.flag_orphans` (job id `flag:<schedule id>:<ulid>`). Each run does at most 500 operations (a reference changed, a link flagged or restored), appends `Schedule.OrphansChecked` and, if work is left, queues the next run; what is left is found from state (references whose presence differs from the snapshot, active links of absent references, links this module flagged on present ones), so a job lost or run twice changes nothing wrong. Flags are written with the actor and event source `svc:schedule`, and a link counts as *flagged by the module* when the source of its latest `Link.Flagged` event is that service, so the module restores only what it flagged and a person's flag stays. **Caps:** at most 100 links to one activity reference and at most 60 000 references per schedule (a link or a reference beyond is refused), so the work per publish is bounded. **The window:** between the publish and the last run of the job, a link to a removed activity still reads as current (the schedule's detail view says `links_being_checked` while the job has work left); `tl xer worker` runs the jobs, and `tl xer reconcile` queues one when a schedule has references out of step.

### 6. Comparison (`compare.py`)
Between any two snapshots of a schedule (default: the built snapshot with the latest earlier data date): activities added and removed by id; date shifts (the eight dates, in calendar days, positive is later; the time of day is ignored; a date that appears or goes has no shift); total float change in days of each activity's own calendar (a negative change is erosion); logic changes (relationships added, removed, changed in type or lag); percent complete, status and remaining duration; original duration; activities that entered or left the critical set; the shift of the latest early finish as a stand-in for the project finish. Lists are sorted so the same rows give the same comparison; a view cuts them to a limit and says how many there were.

### 7. Access (ADR-0011, ADR-0013)
| Act | Who | Why |
|---|---|---|
| Open a snapshot, attach the XER file (slot `xer`, `Uploaded` only), queue the build, link a record to an activity | any signed-in person | They create an unpublished, immutable snapshot or a link and change nothing a reader of the current schedule sees. Starting an extraction is open for the same reason (ADR-0014 D6). A file is queued once and the same file never twice for a schedule. |
| `DefineSchedule`, `PublishScheduleSnapshot`, `VoidScheduleSnapshot` | document controller or admin (`control.command.<Name>`) | What the project's current schedule is must not be changed by anyone signed in; publishing queues the flagging of links. The controller role exists for controlling acts (ADR-0013); a planner who is to publish holds it. Publishing refuses a data date more than 31 days after today (the handler's clock, which a simulation can set): a far-future date would sit above every later snapshot and freeze the series. |
| `ImportCostSnapshot` (apply) | admin | The figures are money and Phase 1 has no cost role; a follow-up if the owner wants one. The preview (the plan) writes nothing and is open to any signed-in person. |
| `tl xer worker`, `tl xer reconcile` | admin (a process that writes as the service) | Operations, not planning acts. |
| Reads (schedules, snapshots, comparison, resolution, look-ahead, cost codes) | `document.read`, so agents may read | |
| Agents | propose only | `PublishScheduleSnapshot` is a proposable command (access `controller` for the person who accepts). No agent tool changes a record. |

The upload slots `report` and `raw` are written by the module only (the snapshot's upload guard, as ADR-0014 for derived documents).

### 8. Reading, reports and the lake
Every surface reads through the module views (`tl_mod_schedule.views`, `tl_mod_cost.views`): the API routes, `ApiClient`, the TUI client (`F12`), the CLI (`tl xer`, `tl cost`) and thirteen MCP read tools. Two small reports decide a little themselves and are module functions with tests: `tl_mod_cost.reports` (budget against forecast per cost code and unit, with the variance, the percentage spent and the number of linked records; the records of a type with no cost code) and `tl_mod_schedule.reports` (the records of a type with no active link to an activity, of one schedule or any). The IWP-versus-activity report of the plan is the second of these asked for the type `awp.IWP`: the work-package records arrive in Phase 2, so the type is an option and the report is empty until they exist. The lake carries the snapshots in a second pass of `tl lake sync` (section 4).

## Consequences
- Contracts: none changed in `tl_core`. New: two entry points `throughline.modules`, the workspace package `tl-xer`, the job kind `schedule.build` in the existing queue, `ScheduleTables` (an operational-table projector like `JobQueueTables`).
- Schema (all additive, ADR-0008 decision 6): `schema/modules/cost/**`, `schema/modules/schedule/**`, the snapshot workflow and file-slot fixtures. Eleven event types; tables `cur_cost_costcode`, `cur_cost_cost_snapshot`, `cur_cost_snapshot_value`, `cur_schedule_schedule`, `cur_schedule_schedule_snapshot`, `cur_schedule_activity_ref`, and the six `sched_*` tables.
- Security review: the XER reader, its envelope and wire checks, the job kind, the access table, the upload guard, the orphan flagging job and its caps, the commands and routes.
- Known limits: no re-pinning of a link by a person to another snapshot in the TUI (use `RepinLink`); moving a mirrored cost code to another parent is refused; XML and API imports of P6 are later connectors that produce the same snapshot structure; the settle transaction holds the writer lock while it writes the typed rows (about 13 s on SQLite and 25 s on Postgres at the maximum snapshot; the claim is 600 s); links show stale only after the flag job has run (the window; `links_being_checked`); resource assignments (`TASKRSRC`) and baselines inside one XER file are in the raw bundle only; an XER with several P6 projects reads one of them.

## Alternatives considered
| Option | Why not |
|---|---|
| One module for cost and schedule | Record types must start with the module name; `m11.*` names would not match the brief's records |
| Parse inside the upload request | Up to 60 s of CPU in a request; a worker holds the limits and the retry rules (ADR-0014) |
| Typed rows as event payloads | Megabytes per event and per snapshot; every projector and the lake would carry them (ADR-0014) |
| Typed rows as projections that read the file | A projection must be a function of events; reading object storage during a rebuild is neither deterministic nor fast |
| A PyPI XER library | A new dependency with its own parsing limits to audit; the format is small and the bounds are the point |
| Links to the snapshot row | The row changes every upload; the stable id is the brief's requirement |
| A new link relation `scheduled_by` | The vocabulary is the thirteen of brief 7.1 and is not yet extensible by modules; `references` plus the type of the target says the same |
