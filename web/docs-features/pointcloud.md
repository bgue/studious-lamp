# Point clouds (as-built check)

Open a laser scan or photogrammetry cloud next to the model and answer one question: is this duct where the model says it is. The cloud is drawn as points in the main scene (depth tested against the model, also when the model is ghosted), aligned to the model, and compared with the model's surfaces. Points are coloured green, amber or red by how far they are from the nearest surface.

Where: the `Scan` tool in the action panel (a drawer), the `Point cloud` folder in the parameter panel, and the command palette. Scripting: `window.__xrayPointCloud`. Drop a `.las`, `.e57`, `.ply`, `.pcd`, `.xyz`, `.pts` or `.txt` file anywhere on the viewer to open it (a capture-phase listener claims the drop before the model loader, only when every dropped file has one of these extensions; a `.laz` drop is claimed too, to show the conversion hint).

## Workflow

1. `Open point cloud`, or drop the file. The status line shows the original and the shown count, the format and the parse time.
2. Check the placement. Clouds written in the model's IFC project coordinates (what most survey and scanning tools export for a building) land in place with `coordinates` = `project`. A cloud already in viewer coordinates (metres, Y up, shifted like the model) uses `viewer`. A cloud in its own scanner frame (a phone LiDAR scan from Polycam, Scaniverse, 3d Scanner App or SiteScape: metric, gravity aligned, any origin and heading) needs `Align by 3 points` (or `Auto-align to model` when it covers the whole building), then `Refine (ICP)`; the manual `offset x/y/z` and `rotation (deg)` nudge on top. Y-up exports (most phone apps' PLY and OBJ-derived clouds) use `coordinates` = `viewer`, Z-up exports (LAS, E57, most survey tools) `project`.
3. Select the elements to check (optional) and pick `deviation scope`: `all elements` measures the distance to the nearest surface anywhere in the model, `focus only` to the surfaces of the current focus set (the selection and what Algorithm 1 treats as focus). Set `tolerance (m)` (default 0.02) and press `Compute deviation`.
4. Read the colours, the legend (bottom right of the viewer) and the numbers in the status line and the drawer.

Panel entries (`Point cloud` folder), exactly: `Open point cloud`, `visible`, `point size`, `colour by` (rgb, intensity, height, classification, deviation), `point budget`, `coordinates` (project, viewer), `Auto-align to model`, `keep vertical`, `allow scale`, `align within` (whole cloud, section box, selection), `Align by 3 points`, `Refine (ICP)`, `Undo alignment`, `Reset alignment`, `offset x`, `offset y`, `offset z`, `rotation (deg)`, `Compute deviation`, `tolerance (m)`, `deviation scope` (all elements, focus only), `Remove point cloud`, read-only `Point cloud status`. The drawer adds `size attenuation`, an explicit `Apply budget` button, and in the 3-point mode the pair list with `Undo last`, `Cancel` and `Apply alignment` (`Refine (ICP)` reads `Stop ICP` while it runs), and after an ICP run the drift grid under the button. Palette actions, without default keys: `pointcloud.open`, `pointcloud.toggle`, `pointcloud.deviation`, `pointcloud.align3`, `pointcloud.refine`. The params document has a `pointcloud` section with the display and alignment settings only (not the data): visible, pointSize, sizeAttenuation, colourBy (a deviation colouring is stored as rgb, since the result is not part of the document), budget, coordinates, offset, rotationDeg, matrix (the registration, 16 numbers, column-major), keepVertical, allowScale, tolerance, scope (`align within` is a step of the workflow and is not stored). A document without `matrix` (written before it existed) reads as no registration, so its offset and rotation mean what they meant.

## Formats

| Format | Read | Notes |
| --- | --- | --- |
| LAS 1.0 to 1.4 | uncompressed | Point formats 0 to 3 and 6 to 8 (4, 5, 9, 10 too: the waveform bytes are skipped by the record length). Scale and offset applied in double. Intensity, classification (5 bits for formats 0 to 5, a full byte for 6 and up), RGB (16 bit; values that fit 8 bit are taken as 8 bit stored in 16). 1.4 files with the legacy count 0 use the 64-bit count. A truncated body is read as far as it goes and reported as a warning. |
| LAZ | no | Rejected with: convert with PDAL (`pdal translate in.laz out.las`) or LAStools (`las2las -i in.laz -o out.las`). Detected by the extension, the compression bit in the point format and the `laszip encoded` VLR. |
| E57 (ASTM E2807) | bitPackCodec (the only codec the standard defines) | What terrestrial scanners and most iPhone / iPad LiDAR apps export. Every scan under `data3D` is read and the scans are merged into one cloud, each placed by its `pose` (quaternion and translation, applied in double); more than 100 scans are merged too, with a warning. Coordinates: `cartesianX/Y/Z`, or `sphericalRange/Azimuth/Elevation` converted to Cartesian; Float (single, double), ScaledInteger and Integer fields of any bit width (bit packed, LSB first, across data packets; index and empty packets skipped). Points with a non-zero `cartesianInvalidState` / `sphericalInvalidState` are skipped. Intensity is normalised to 0..1 by the scan's `intensityLimits` (else the field's bounds), colour by `colorLimits` (else the field's bounds, e.g. 16-bit colour from LAStools); `isIntensityInvalid` / `isColorInvalid` are honoured; a scan without colour next to coloured ones is drawn grey. E57 is Z up in metres like IFC project coordinates, so the default `coordinates` = `project` applies. The 1024 byte pages' CRC-32C checksums are verified; a mismatch is a warning (libE57Format would refuse the file), not an error. A cut-off file keeps the points read so far and says so; a file whose XML section is missing is an error. Not read: `images2D` (the status line says how many photos were left out; a file with photos and no points says there is nothing to draw), other codecs (the error names the codec and suggests a re-export or a conversion with CloudCompare or `pdal translate in.e57 out.las`), extension fields. Own reader (no libE57Format); the XML goes through the DOM free parser of the BCF feature, so it runs in the worker. |
| PLY | ascii, binary little and big endian | Vertex properties `x y z`, `red green blue` (or `r g b`, `diffuse_*`), `intensity` (also `scalar_intensity`, `reflectance`), `classification` (also `class`, `label`). `float` and `double` coordinates. Faces and other elements are skipped. Own reader (three's PLYLoader would round double coordinates to Float32 before the offset can be removed). |
| PCD | ascii, binary, binary_compressed | Fields `x y z`, `rgb`/`rgba` (packed float or uint32), `intensity`, `label`. LZF decompression is built in. NaN points (organised clouds) are dropped. |
| XYZ, TXT | text | Whitespace, comma or semicolon separated: `x y z`, `x y z i`, `x y z r g b`, `x y z r g b i`. Comment and header lines are skipped and counted. Colour scale (0..1, 0..255, 0..65535) is detected. |
| PTS | text | First line is the point count; `x y z i`, `x y z r g b`, `x y z i r g b` (intensity before colour, as Cyclone writes it). |

The format is taken from the first bytes (`LASF`, `ASTM-E57`, `ply`, `# .PCD`) before the extension, so a mis-named file still opens.

Files over 5 MB are parsed in a Web Worker with progress in the status line; smaller files, and any environment without workers, parse inline. Typed arrays are transferred, not copied.

## Precision

Positions are kept as Float32 relative to the first point, whose double precision coordinates are stored separately. A georeferenced cloud (coordinates around 2 600 000, 1 200 000) therefore keeps millimetres. The large offset only appears in the cloud's 4x4 matrix, which is composed in double and applied by three.js on the CPU in double, so the GPU sees small numbers.

## Point budget

`point budget` (default 3 000 000, slider up to 10 M) caps the points drawn. Decimation is uniform random sampling without replacement (selection sampling, one pass, seeded, exact count, original order). Why not a voxel grid: random sampling is exact, O(n) and a few milliseconds per million points, and it is an unbiased sample, so shares and percentiles measured on it estimate those of the full cloud. A voxel grid evens out density and keeps thin features but needs a cell-size search to hit a budget and is much slower. The worker keeps the full cloud, so changing the budget re-samples it without parsing again (`Apply budget` in the drawer, on release of the slider in the panel). The status line shows `N points, M shown`; the same numbers are in `stats.originalCount` and `stats.shownCount`.

## Alignment

The cloud is drawn with a general rigid (or similarity) transform composed in double:

```
p' = N * A * (g + base)          N = T(A pivot + offset) * Ry(theta) * T(-A pivot)
```

`g` is the Float32 position (axis mapped), `base` the mapped double origin, `pivot` the mapped bounds centre. `A` is the registration (`matrix`, a 4x4 set by 3-point alignment or ICP, identity by default), `N` the manual nudge (`offset x/y/z`, `rotation (deg)` about the vertical through the registered bounds centre). With `A` the identity this is the original `p' = Ry(theta) (g + base - pivot) + pivot + offset`, operation for operation, so project-coordinate clouds and old documents land exactly where they did. `c = g + base` is the cloud frame of the registration code; `N A` maps it to the viewer.

When a solve gives a pure heading plus a translation (always with `keep vertical`), it is stored as `offset` and `rotation (deg)` with `A` the identity, so the panel shows the real numbers and a nudge works as before. A tilt or a scale is stored in `A` with a zero nudge; the status line then names heading, tilt and scale.

- `coordinates` = `project`: the cloud is in IFC project coordinates (Z up). The viewer mapping is `v = (x - sx, z - sz, -(y - sy))` with `s` the model's `originShift` (verified against `tools/glb_common.py`, which rotates (x, y, z) to (x, z, -y) after subtracting the shift; the BCF feature uses the same). Also the choice for any Z-up scan in its own frame (the shift then does no harm).
- `coordinates` = `viewer`: used as is (Y up). The choice for Y-up phone exports.
- `offset x/y/z` (metres, viewer frame, applied after the mapping and the registration, shown to 0.1 mm) and `rotation (deg)` (positive turns counter-clockwise seen from above, which is also positive about IFC Z).
- `Auto-align to model`: moves the cloud's bounds centre onto the model's bounds centre (all three axes), then tries 0, 90, 180 and 270 degrees about the vertical axis and keeps the angle with the smallest median distance of 2000 sample points to the model. A coarse start for a scan of the whole building; a scan of one room needs `Align by 3 points`. It replaces the whole alignment (registration included).
- `keep vertical` (default on): 3-point alignment and ICP solve heading and translation only (4 degrees of freedom). Phone LiDAR (ARKit), tripod scanners and SLAM devices give gravity-aligned clouds, so a tilt is almost always a picking error. Off: full 3D rotation.
- `allow scale` (default off): 3-point alignment also estimates one uniform scale (Umeyama). Phone and laser scans are metric; a scale far from 1 (beyond 5 percent) is reported as a warning. ICP never changes the scale (it keeps what the registration has).
- `Undo alignment` steps back through the last 20 alignment actions (Auto-align, 3-point, ICP, reset, script `setMatrix`); `Reset alignment` clears offset, rotation and registration.

### Align by 3 points

A guided mode in the Scan drawer. Click a point on the cloud (cyan numbered circle), then the same feature on the model (orange numbered square); repeat 3 times or more. A dashed line joins each pair and carries its residual after the solve. `Undo last` removes the last pick, `Cancel` (or `Escape` when no cloud point is pending) leaves the mode without a change; `Escape` with a pending cloud point removes that point. Closing the drawer cancels the mode. `Apply alignment` sets the solved transform; the drawer lists the residual of every pair and the RMS while you pick.

- Cloud picking: the shown point nearest to the cursor on screen. A screen-space index (each shown point projected once per view into 8 px cells, a counting sort; rebuilt only when the camera, the transform or the drawn subset change) answers a click or hover in microseconds; building it for 2 million points takes tens of milliseconds. First the points whose drawn square covers the cursor (point size / 2 + 1 px) compete, frontmost first; only when none does, the 8 px radius. Among the candidates the frontmost depth `d0` wins, with a band of max(5 cm, 1 percent of `d0`) inside which the one nearest the cursor is taken (a plain "frontmost in 8 px" picked the top edge of a wall beside a floor spot: in perspective it projects over the floor). Points removed by a section plane are not picked, nor points hidden behind an opaque model surface: the first surface along the camera ray through the cursor (hidden elements skipped, ghosted ones with alpha below 0.5 skipped too, since a ghost is drawn see-through, and the side a section plane removes ignored) gives a view depth, and only points up to that depth plus the depth band compete (`PickOptions.maxDepth` in `pick.ts`). Before, a click on a wall picked the floor points of the room behind it.
- Model picking: exactly the measure tool's surface pick (first surface along the camera ray through the merged BVH, hidden elements skipped, ghosted ones count; snapped to a vertex of the hit triangle within 12 px, which makes corners easy).
- `align within` = section box or selection: only the pairs whose model point lies in the region are solved (the list marks the others "outside the region, not used", and a warning counts them).
- Solve (`src/pointcloud/register.ts`): least squares over all pairs. Full 3D: Horn's closed-form quaternion method (no reflection or 180 degree case to handle), with the Umeyama scale when `allow scale`. `keep vertical`: 2D Kabsch on the horizontal plane (x, z) for the heading, and the mean vertical offset (2 pairs suffice). Warnings: too few pairs; nearly collinear points (second principal spread below 8 percent of the first, full 3D only; below 1 percent the solve refuses); points stacked on plan (`keep vertical`); a large residual (RMS over 5 cm or a pair over 10 cm, naming the pair); an odd scale.

### Refine (ICP)

Trimmed point-to-plane ICP (`src/pointcloud/icp.ts`) of 20 000 cloud points against the model surface of the `deviation scope` (merged BVH, or the focus elements' BVHs), with the closest point and the hit triangle's normal from `closestPointToPoint`.

- Sample: spatially even, by Poisson-disk thinning on a voxel hash grid (visit the points in a fixed random order, keep one when no kept point lies within `r`, `r` searched for the count). Not "one point per voxel": on a noisy surface a voxel boundary inside the noise band gives both halves a representative, which shifts the sample off the surface by a good part of the noise (8 mm for 1.5 cm noise on the building floor, which ICP then registered as a 1.1 cm vertical error); the disk rule does not depend on where the grid starts.
- Normals (`src/pointcloud/normals.ts`): PCA of the neighbours of each sample point, taken from a denser copy of the cloud (the shown points in the region, thinned by a stride to at most 100 000; grid hash): the 16 nearest, or, when they lie closer than 16 times the noise estimate (a dense scan, where a neighbourhood as wide as the noise is thick has no plane), up to 48 points spread over that radius (at most 8 dense spacings). The noise estimate is the median spread along the normal of the 16 nearest of 2000 dense points. Why the dense copy and not the sample's own neighbours: the 20 000 point sample of the whole building has 12 cm spacing against 20 cm walls, so its 16 nearest straddle both faces (only 400 of 20 000 sample points found a plane). Points whose neighbourhood is no plane (variance along the normal above 6 percent of the total: edges, corners, clutter) get no normal and do not take part. Orientation: (1) towards the scanner when the file's own origin lies inside the cloud's bounds (plus 1 m): a phone scan starts at its origin, a single terrestrial scan sits at it; not when the normal grazes the line of sight, nor when a tube along the normal on the scanner's side holds points (the point was then seen from elsewhere, past something in front of it); (2) without a scanner position, occlusion: a scanner cannot see a point through other points, so a tube along the normal (balls of 0.9 times the median distance to the 16th nearest dense point, about 4 points of a crossing surface, from beyond 4 times the noise to 0.6 m) that holds points on one side (the other face of a wall, the slab under a floor) and none on the other is seen from the empty side. Not used when a scanner position is known: a wall seen obliquely past a chimney has the chimney in its tube, and the rule would flip it. (3) Otherwise an axis only. The estimate runs time sliced before the ICP (1 to 3 s in swiftshader; `Stop ICP` cancels it too).
- Normal compatible pairs: the closest model surface whose triangle normal lies within 40 degrees of the cloud normal (a shapecast on the BVH with the normal test, `src/pointcloud/surface.ts`), so a noise point beyond the middle of a thin wall still finds the face it belongs to and not the far face 2.4 cm away. With an orientation the facing counts too (dot above cos 40 degrees), without one the axis (|dot|). Which convention the model's faces follow is measured, not assumed: at the start of the full run (after the heading search) the share of the oriented cloud normals that face the same way as their axis-compatible surface decides: at least 0.8 uses the orientation, at most 0.2 uses it flipped (a model whose faces point inwards), else the axis only; when a rough start hides it, it is asked again at the end of the run and a short polish follows. The heading search weights each start's share within 4 cm by the square of that agreement (a wrong fit puts points on faces that look the other way: 0.79 against 0.96 on the phone scan). Before and after are always scored with the axis rule, so the guard compares like with like. `refine({ normals: false })` turns it off.
- Per iteration: pairs within the maximum distance, then the best 85 percent of them (trim); linearised point-to-plane least squares about the inlier centroid (6 unknowns, 4 with `keep vertical`; slight damping keeps a single plane solvable); the exact rotation is applied. The maximum distance starts at max(0.5 m, 3 x the RMS within 2 m) and shrinks to 3 x the inlier RMS, by at most 15 percent per iteration, not below 2 cm (a quick shrink locked in a local minimum: the floor fits at once and pulls the RMS down while the walls still disagree). Stops when a step moves less than 0.1 mm and turns less than 0.01 degrees, or after 30 iterations.
- Heading search first: short runs (10 iterations, 2500 points) from the start turned by 0, +-5, +-10 and +-15 degrees about the vertical; the start with the most points within 4 cm (by a clear margin over a smaller turn) is where the full run begins. Reason: walls are two-sided; turned 10 degrees, the half of a wall that moved behind its inner face matches the outer face 20 cm further and cancels the turn, so a single run stopped at 7 degrees in the building test.
- Guard: start and end are scored with the same maximum distance and trim. When the RMS got worse or the inlier share halved, the previous alignment stays and the status says so. Fewer than 12-18 points near the model: refuses with "align roughly first".
- Time sliced on the main thread like the deviation (8 ms slices, longer when frames in between are slow, a yield between them), progress in the status line, `Stop ICP` cancels. The result line gives iterations, the heading the search kept, whether oriented normals were used, RMS and inlier share (of the points with a normal) before and after, how far it moved and turned.
- `Stop ICP`: the drawer's status line never shrinks while the drawer is open (it scrolls beyond 7 lines), so a short progress line after a long result no longer pulls the button up under the pointer, and the button acts on the label the user saw (`data-mode`), not on the state when the click arrives: a click that lands just after the run ended (within 0.6 s) does not start a new run. Before, a browser test could not stop a run: the button jumped by 16 to 48 px with every status change and, by the time the click went through, the run had ended and the click started a new one.
- `align within` (section box: the active box of the Section tool, read from `window.__xraySection`; selection: the bounds of the selected elements plus 0.5 m): ICP samples only the shown points whose current position lies in the box (the Poisson sample and the normals are taken from those), and 3-point alignment solves only the pairs in it. The result is still one rigid transform for the whole cloud.
- Drift diagnostic: after the run, the matched points are binned into a 3 x 3 plan grid over their extent (viewer x east, z south; north up in the drawer). Per cell: count, residual median and RMS, and the local misfit, the translation that would fit that cell's pairs on their own (damped point-to-plane least squares; noise averages out of it, so a systematic offset shows where the residuals are dominated by noise). The drawer shows the misfit per cell (amber from 1.6 x the typical cell, red from 2.5 x and 4 mm); when the worst cell is 4 mm or more and 2.5 times the median cell, the status line says "The fit degrades towards the north-east: that part sits 7.7 mm off (typical 2.6 mm), so the scan may bend (drift)." (`stats.icp.regions`, `stats.icp.drift`).

#### Room by room

A long phone walk drifts (the heading bends slowly with distance), and a rigid fit spreads that over the whole cloud: the middle fits, the ends pull apart. To check one room at a time: put a section box around the room (or select its walls and slab), set `align within` to section box (or selection), pick 3 pairs in that room (the pairs elsewhere are left out) or start from the current fit, `Refine (ICP)`, `Compute deviation` and read the room. Then move the box to the next room and repeat. Each step replaces the transform of the whole cloud (one cloud, one transform; `Undo alignment` steps back), so the deviation is valid for the room the box holds. Saving several alignments side by side is not provided: a view (or a params document) per room keeps each room's matrix.

Measured on `building` with `building-phone-scan.ply` (one room, heading 37 degrees, 1.5 cm noise; `bench/smoke-pointcloud-align.mjs`, swiftshader): 4 pairs clicked on floor spots gave 1.6 cm pair RMS and a transform within 0.08 degrees / 5.5 mm of the truth; ICP with oriented normals brought it to 0.014 degrees / 0.12 mm (6 iterations; 16 400 of the 20 000 sample points had a normal, 15 700 an orientation), and from deliberately rough starts (10 degrees / 0.3 m, 15 degrees / 0.5 m, 10 degrees with a 1 degree tilt in full 3D) to 0.01 to 0.05 degrees / 0.2 to 1.4 mm. Without normals it stopped at 2.4 mm, 2.3 mm of it sideways: the 2.4 cm plumbing wall, whose two faces lie within the noise of each other, pulled the cloud towards its far face. In Node on the same data (`tests/pointcloud-icp-building.test.ts`): 2.44 / 2.63 / 2.55 mm without normals, 0.48 / 0.44 / 0.56 mm with, from the truth, 10 degrees and -15 degrees. On the survey scan `building-scan.ply` from 10 degrees without the heading search, ICP without normals locked onto the wrong faces of the 20 cm walls (0.48 degrees / 23 mm); with normals it reaches 0.006 degrees / 0.20 mm. Median deviation afterwards 9.5 mm (the expectation for 1.5 cm Gaussian noise is 0.67 x 1.5 = 10 mm). Numbers before and after: `bench/RESULTS-pointcloud-w7.md`.

Changing the model, the coordinates mode, the alignment (any of the above), the budget or the tolerance clears a deviation result (the colours go back to the previous mode), because it no longer describes what is on screen.

## Rendering

`THREE.Points` in `app.renderer.scene` with a `PointsMaterial` (vertex colours, size in CSS pixels, optional size attenuation where `point size` is the size at the orbit target). The points are in the opaque queue, drawn before the ghost pass: the ghost (which writes depth) then blends over them instead of hiding them, so points stay visible when the model is ghosted, and they are depth tested against opaque meshes. The focus pass is drawn last and in front by the renderer, so it covers points inside the focus element's silhouette. To keep deviation findings visible anyway (a displaced duct inside a ghosted host), the amber and red points are drawn a second time as `pointcloud-findings`, without depth test, after every other pass (they share the buffers); green and unrelated points keep normal depth behaviour. Colour modes: `rgb` (a height ramp when the file has no colour), `intensity` (grey, stretched over the file's range), `height` (viridis ramp over the cloud's height range), `classification` (ASPRS palette), `deviation` (bands, grey until computed). Section planes: when `app.renderer.getClipPlanes()` exists, its planes (normals towards the kept side, the convention three.js clipping uses too) are copied onto the material every frame and `localClippingEnabled` is on. Raycasting is disabled on the cloud, so picking and hover keep using the model.

## Deviation

For each shown point (a stride sample of at most 500 000 when more are shown; then only the measured points are drawn while colouring by deviation) the distance to the nearest model surface is taken with `closestPointToPoint` on the merged geometry's BVH (`all elements`) or on the focus elements' own BVHs (`focus only`, needs a selection). Distances are searched only up to `max = 5 x tolerance`. The work runs on the main thread in time slices of 8 ms (longer when a frame in between was slow) with a `setTimeout` yield between them, so the page stays responsive and shows progress; changing the alignment or removing the cloud cancels it. (A worker with a serialised BVH would give a lighter main thread but needs the model geometry copied and rebuilt there; not done.)

| Band | Distance d | Colour |
| --- | --- | --- |
| within tolerance | d <= tol | green |
| up to twice | tol < d <= 2 tol | amber |
| beyond | 2 tol < d <= 5 tol | red |
| unrelated | d > 5 tol (or no surface that close) | grey |

Statistics (`stats.deviation`, the status line and the drawer): `shareWithin` is the share of related points (d <= max) within the tolerance; `shareWithinOfAll` counts the unrelated ones too; `mean`, `median` and `p95` are over the related points; `unrelatedShare`; counts per band; and, when the cloud has classification codes, `byClass[code] = { n, related, shareWithin, shareRed, median }`. Unrelated points are not an error: they are scan of something the checked elements do not contain (furniture, other objects, a point cloud of a different room). With `focus only`, everything except the selected elements is therefore mostly grey, and the colours and numbers say how well the focus elements are matched.

## Scripting

```js
const pc = window.__xrayPointCloud;
await pc.load(fileOrArrayBuffer, 'scan.las');   // resolves with stats
pc.settings.tolerance = 0.03; pc.controller.setTolerance(0.03);
pc.autoAlign(true);                             // { offset, rotationDeg, description }
pc.pairs.start(); pc.pairs.clickAt(x, y);       // 3-point mode: cloud, model, cloud, ... at client positions
pc.pairs.addCloud(c); pc.pairs.addModel(v);     // or give the points (cloud frame, viewer frame)
pc.pairs.solution;                              // { matrix, residuals, rms, warnings, scale, ok }
pc.pairs.apply();                               // set it (undoable)
await pc.refine({ samples: 20000 });            // ICP; IcpResult { ok, reverted, iterations, before, after, normalMode, regions, ... }
await pc.refine({ normals: false });            // without normal compatibility
pc.settings.alignRegion = 'section box';        // or 'selection', 'whole cloud'; pc.controller.regionBox() gives the box
pc.matrix; pc.setMatrix(m16); pc.undoAlignment(); pc.resetAlignment();   // total transform, cloud frame -> viewer
const s = await pc.computeDeviation();          // DeviationStats, or null (no cloud, no model, empty focus)
pc.stats;     // { loaded, name, format, originalCount, shownCount, parseMs, decimateMs, mode, warnings, deviation, deviationMs, icp: { normalMode, region, regions, drift, ... }, ... }
pc.remove();
```

## Sample data

`tools/make_pointcloud.py` samples the surfaces of a converted model (default `web/public/models/building`) into a synthetic as-built scan: area-weighted random points, Gaussian noise (sigma 5 mm per axis), the duct displaced 80 mm horizontally and diagonally to the walls (so every face is off by about 57 mm), and a 10 percent band missing from every wall (an incomplete scan). It writes `web/public/samples/building-scan.las` (LAS 1.2, point format 2, 1 mm scale), `building-scan.ply` (binary little endian: float xyz, uchar rgb, intensity, classification) and, when pye57 is installed, `building-scan.e57` (ScaledInteger xyz at 1 mm, 16-bit intensity, 8-bit colour, no classes since E57 has no standard class field; 2.2 MB) in IFC project coordinates, unshifted, with ASPRS classes (walls 6, slabs and footings 2, duct 19, the rest 1). About 221 000 points each; the files stay under 6 MB (LAS format 2 is 26 bytes per point). Seeded, so reruns give the same files. Other models: `--model web/public/models/fzk-haus --name fzk-haus-scan`.

`--phone` writes `web/public/samples/building-phone-scan.ply` instead (150 000 points, 2.3 MB): what a phone LiDAR app exports for the back room of the house. Only surfaces inside a box around the room whose faces turn towards one of 4 stops of a walk through it, nothing above 0.6 m viewer height (no ceiling, so partial walls), Y up in the scan's own frame with the origin at the scan start (1.3 m above the floor) and a heading of 37 degrees (`--heading`), 1.5 cm noise, shuffled order, optional heading drift (`--drift` degrees per metre from the start). Binary little endian PLY with float xyz and uchar rgb; the true transform is a header comment (`comment truth: viewer = Ry(37 deg) * p + (tx, ty, tz)`, for `coordinates` = `viewer`), which the tests and the smoke script read.

## Limitations

- One cloud at a time. No LAZ, no E57 images or compressed codecs other than bitPackCodec, no PLY with list properties on vertices. Points are picked only for 3-point alignment (no measuring on the cloud).
- Single-file bundles: the worker URL is not inlined, so there the cloud is parsed on the main thread (the loader falls back when the worker fails to start).
- Auto-align is a bounds-centre match plus a 90 degree search; scans that cover only part of the building need `Align by 3 points`. ICP is rigid: drift inside a long phone scan (a bent corridor) stays as a residual (the drift grid shows where; `align within` fits one room at a time), and its basin is about 15 degrees and half a metre. A thin element scanned on both faces, with no orientation for its normals (no scanner origin, nothing behind it), can still bias ICP by a millimetre or so, symmetrically. Normals need a plane around the point: a sample of only edges and clutter (under a quarter with a normal) runs without them. Scale only from 3-point alignment.
- Deviation is the distance to the nearest surface, not along a normal, and takes no account of which side of the surface the point is on. Distances beyond 5 x tolerance are not measured.
- Points are square, constant-colour pixels; no eye-dome lighting, no level-of-detail tree. The budget is the only performance control, so very large clouds are a sample.
- The ghost pass with order-independent transparency is drawn from private scenes; the cloud takes part in the main scene's depth only.
